# 010 Half-precision vector FNEG produced C++ that does not compile

**Symptom.** Building Fortune's Weave's `sdk` (nnSdk 22.2.0) failed in one translation unit: `error: no member named 'f16' in 'V128'`
at four statements `r.f16[k] = uint16_t(-S.f16[k])`. `cover` had reported the module 100% translated. The words are
`fneg v2.8h, v2.8h` and the like at 0x750014f350, 0x750014f3a0, 0x750014f3dc and 0x750014f408 (an SDK routine over 16-bit
characters): LLVM makes the lane constant 0x807e with `movi v.8h, #0x7e` and a half-precision `fneg`.

**Cause.** Tier 1 does not decode the FEAT_FP16 vector encodings, so they reach tier 2. The ported FP lane emitters (`v_un`, `v_bin`,
`fac`, `v_cvt_to_int`, `faddp`) name the V128 view after the element size (`f32`, `f64`), and V128 has no half-precision view.
Emitting text never failed, so `cover` counted the words as translated. The scalar half forms (`fneg h0, h1`) compiled, but went
through `f16_to_f32`, which quietens a signalling NaN; FNEG and FABS never quieten.

**Fix.** `x_fp.py` handles FNEG and FABS of half precision (v.4h, v.8h, h) as the sign-bit operations they are, on the integer lanes
(`^ 0x8000`, `& 0x7fff`); single and double precision keep their path (tier 1 takes them first anyway). `Tier2.lift` refuses any
statement that names `.f16[`, so the remaining FEAT_FP16 vector forms are reported as not translated (`t2:<mnemonic>:half-precision
lanes`, `guest_unimpl` at run time) instead of breaking the build. Fortune's Weave has only the four `fneg` words; Pokopia's
modules have none of these forms (its build compiled).
