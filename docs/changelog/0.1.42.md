# EmblemWeave 0.1.42

> Cinematic playback infrastructure, Find Units optimization, title-return crash mitigation, HDR exit handling (original-state restoration outstanding), and save-directory reconciliation. Field verification is pending for the runtime items.

**Status: unreleased.** 0.1.42 is in development; 0.1.41 is the current public release. These are the draft notes
for the next release and describe work on the development tree, not a published build. The site and the updater
keep pointing at 0.1.41 until the engine work is finished and the release is tagged.

## Diagnostics and renderer instrumentation (not yet measured)

- **Renderer profiling.** `[prof] renderer_profiling = true` now records frame-time P50/P95/P99, shader translation
  and module-creation time, pipeline creation (graphics/compute, cache hits and misses, linked-from-parts, prewarm
  takes), texture create/destroy/upload/transcode, staging and copy time, render-thread phase time, submission counts,
  GPU-sync waits, GPU memory from the VMA gauges and the prewarm counters. `[prof] renderer_csv` writes one row a
  second. Off by default. **No overhead measurement has been made**; the counters are what a before/after comparison
  will need.
- **Memory snapshot in the device-lost report.** Process and system memory, every gauge, the VMA budget and live
  percentage, the deferred-destruction queue depth, the thread registry and the recent-file ring are written next to
  the GPU device-lost message, so a crash report from a player carries the evidence for #37/#41.
- **Bounded pipeline prewarm.** `[nvn] prewarm_max_queue` bounds the queue, `prewarm_metadata_priority` orders it by
  how often and how recently a key was drawn, and `prewarm_recency_decay` is now honoured. Drawn pipelines are no
  longer built ahead when the queue is full; they build at their draw as before.
- **`[gfx] frame_wait_ms`** (default 1000) bounds the frame-slot and swapchain-image waits. A GPU or compositor that
  stops answering costs skipped frames (and a swapchain rebuild after three in a row) instead of a frozen window.
- **Fewer console windows.** Build probes, `git rev-parse`, the Python probe and the ReShade setup no longer flash a
  console window when started from the launcher.

These are described from the code, not from a run: no game session, cinematic, save load or long session was
performed while they were integrated.

## Critical Fixes

- **Issue #77: Crash returning to title (implemented; field verification pending).** One 120-second session (4000+ frames) completed without the write fault crash at ~4s, the read fault crash at ~6.3s, or "second exception inside crash handler" at ~8s. Root cause was ImportFreeze making pages read-only before installing the page fault handler, and the handler lacking broad fallback for PAGE_NOACCESS pages left by the Vulkan driver. A scripted 10-cycle run has since passed twice: 10 gameplay -> title -> gameplay cycles, 21 screenshots each, exit 0 and no crash. A preserved run from 2026-11-24 05:30 recorded 35,144 frames and 448.9 s; the current working-tree engine binary recorded 31,301 frames and 456.7 s with 0 error lines, 0 guest traps and 0 zstd errors. The current binary is not a clean archive and the reporter's damaged save was not available, so the exact trigger is not reproduced.

- **Issue #77: A damaged autosave is moved to backups before Play (implemented; field verification pending).** One report's crash happened immediately after the game opened `account/<id>/000/Auto`; the file's zstd frame was damaged (`ZSTD_error_corruption_detected`, error -20) and the guest used the decoder's error code as a copy length. The launcher now opens that slot before starting the game. If it cannot be parsed or verified, the file is moved unchanged to `save/backups/<stamp>-damaged-autosave-Auto`, a `.why.txt` names the reason, and Play stops with a message instead of launching the crash again. A valid autosave is untouched and nothing is deleted. Before accepting the file, the guard decodes the frame with the same zstd library and one-shot call the game uses. This matters because ruzstd accepts a frame whose checksum is corrupt while the payload still decodes, but native zstd rejects it; a regression test builds exactly that frame, proves the payload decodes, proves native zstd rejects it, and proves the guard quarantines it. This does not repair the frame or find why it was damaged, and the reporter's save was not available to test. Launcher tests: 435 passed, 0 failed, 13 ignored, including the damaged, checksum-corrupt and valid autosave cases.

## Startup and audio

- **Loading card while the game boots.** Pressing **Play** now shows a small translucent, always-on-top card that says the game is loading, over the black window while the engine initialises. It follows `fefw.log` and closes 700 ms after the engine logs `startup ready`, which is written at the first frame with 64 or more draws (the loading frames draw 3, the early fade 35, the title 547). Guards close it after 180 seconds, or after 60 seconds without a game process, so a failed start cannot leave it on screen. Measured on this PC: the marker arrived at 14.4 s in the launcher run and 14.9 s in a direct engine run, and the card disappeared as the title screen appeared.

- **Master volume above 100% without the EQ preamp.** The Master slider now applies 0-200% immediately. The confirmation step that made the control read as a hard 100% cap is gone, and the engine no longer waits for a separate boost approval before applying the value; the peak limiter and the row's warning still apply. Verified by moving the launcher slider to 155% with no modal.

- **No startup-time reduction is claimed.** A controlled A/B on this PC took 44.8 s to the first full frame from the packed H: `.nup` and 48.0 s from the extracted E: folder, so moving the RomFS did not help; the time is inside the engine's load and first-frame work.

## Infrastructure and mitigation (field testing pending)

- **Issue #75: Cinematic playback (AV1 + Opus).** dav1d AV1 decoder with x86-64 assembly, WebM AV1CodecConfigurationRecord parsing with variable-length OBU extraction, MP4 av1C fallback, hwopus Opus decoder via FFmpeg (dynamic DLL loading), D3D11VA hardware acceleration configured (8 threads, 30 frames ahead).

- **Issue #76: Find Units cheat stuttering.** Parallel memory scanning with worker threads, cancellation tokens, progress reporting, thread priority BELOW_NORMAL, 30s timeout, 2GB memory limit, 8 thread cap.

- **Issue #78: HDR remains enabled after exit (partial).** `play.cpp` stop() forces windowed mode before marking play stopped. It does not record or restore the monitor's prior Windows HDR state, SDR white level, resolution, refresh rate or HDR10/scRGB format, and it does not cover borderless, initialization failure, device loss or crash paths. Do not read this as HDR state restoration.

- **Rebuilds stopped with "The input line is too long" (FIXED).** `build_game.cmd` calls `nx_env.cmd` once to configure and once to build, and `nx_env.cmd` ran without a scope of its own: the second call's `vcvars64.bat` inherited the first call's `INCLUDE`, `LIB` and `PATH`, and on an already long environment one expanded line passed cmd.exe's 8191-character limit. The build stopped with exit 255 immediately after CMake configured, before Ninja ran a step. `nx_env.cmd` now has `setlocal`, so each call starts from the caller's environment; the command it runs still sees everything it sets. Verified by reproducing the failing run with the environment recorded in the engine log, then rebuilding the game through the launcher (8 of 8 stages).

- **A required tool that cannot report a version now names the path it ran.** The build error said only "not found", which sent the player looking for an install that was already there; it now includes the executable the probe ran when one was found.

- **Rebuilds stopped with "Access is denied" (FIXED).** Toolchain verification ran Visual Studio's expected path, which is the install folder, instead of `vswhere`; Windows answers a folder with `os error 5`, before the first build stage could log a line. The verifier now runs the program the version command names (with an absolute `vswhere`), and folder-backed components — the MSVC toolset and the Windows SDK — verify against the version the probe recorded instead of being reported missing. It also finds the CMake, Ninja and Python the release carries in `engine\fefw-recomp\tools\bin` even when they are not on PATH, and no longer requires .NET when the prebuilt shader translator is present. A `tools.lock` written by an older probe is discarded and regenerated when it cannot locate a required tool or still requires one this release made optional; the stale Nov 21 lock in the engine checkout is one. Verified with the launcher's own generated lock on this PC (Visual Studio 18.12): no required tool missing.

## Issue #79: Save Files Not Being Read (IMPLEMENTED, UNVERIFIED)

- **R1: INI reconciliation.** `sync_save_dir()` in `engine.rs` reconciles `[fs] save_dir` in fefw.ini with `Config::save_dir()` before every Play, fixing the root mismatch that survives rebuilds.

- **R2: UI path display.** Game Setup and Saves pages now show the effective save folder from fefw.ini alongside the configured folder, with a mismatch warning when they differ.

- **R3: Unread saves are shown and adoptable.** `find_orphan_saves()` also finds a save nested one level below the game's own account folder (`account/<user>/<user>/000`), the shape an older import could leave while the game opens the empty folder above it. The Saves page's Current save section now lists those saves with **Use this save**, which backs up the current save first. Profiles stay in the carousel.

- **R4: Runtime loud auto-create.** `save_dir()` in `common.cpp` now logs when it creates the save directory (configured or fallback), making silent auto-creation visible in logs.

- **R5: Diagnostic bundle evidence.** The report's saves section names the configured and effective folders, whether each holds a real save (`000` file count and `.meta` presence), a save nested too deep, unread saves, every other EmblemWeave data root that holds one, and every emulator save found. The report answers the first question of a save bug even when the reporter never attaches the ZIP.

- **R7: Safe reconciliation.** `sync_save_dir()` copies the save out of the INI's folder into the launcher's folder before rewriting the INI. A folder holding only the account's `.meta` now counts as empty, so a real save is carried instead of skipped; the game writes that metadata on first start, before it has saved anything. Play now refuses to start when a save exists but could not be copied, instead of opening an empty game that looks like data loss.

- **R8: Every launcher root is found, and the newest save is carried.** `launcher_sources()` looks at `%APPDATA%\EmblemWeave\save`, `<install>\data\save`, `data\save` of copies extracted beside this one, and the install a remembered `engine.txt` names (which can be on another drive). Before Play, when the folder the game will read has no save, the newest save from another data root is copied in; the source is left untouched and the Saves and Setup pages still list the others for an explicit import.

- **Launcher-level import verified with a real emulator save, not the reporter's failure.** Eden is configured with `nand_directory=C:/Users/xiond/AppData/Roaming/yuzu/nand`, so Eden and Lichii read the same FEFW save under yuzu's NAND. `--import-save` on that folder copied 10 files into the engine's `account/<uid>/000`, wrote the `.meta`, moved the previous save to `backups/`, and left an existing profile byte-identical. Profile import was verified by test: a yuzu title folder becomes a new profile and never replaces a profile or the current save. The issue stays open until the reporter confirms on their own install.

- **Hardening verified by tests, not by the GUI.** 435 launcher tests pass (`cargo test -p emblemweave --locked`), including a `.meta`-only account folder, a save nested below the game's account folder, and a remembered install on another path. The new **Use this save** button was not clicked in a running window.

## Engine Stability

- **write_watch null g_transitions crash (FIXED).** ImportFreeze constructor now lazily initializes `g_transitions` RWLock under mutex and installs fault handler before making pages read-only.
- **Broad read fault fallback.** Handles committed PAGE_NOACCESS pages not tracked by any region.
- **Write fault fallback hardening.** Fallback 1 & 2 check `protect()` return value and balance `g_busy` on failure; Fallback 4 handles write faults on decommitted (PAGE_NOACCESS) pages still in a region.
- **ImportFreeze for all pools.** NVN pool import creates ImportFreeze for all pool types, not just viewed pools.
- **heap_decommit clears retired bit.** Prevents retired page race on scene teardown (commit 406e46f).
