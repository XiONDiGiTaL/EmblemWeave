# EmblemWeave 0.1.43

> Windows SDK 10.0.19041 builds again, the Obelisk Chamber stall is fixed, and the engine picks up the 0.2.12-0.2.13 performance and stability work.

**Status: release candidate, prepared 2026-11-27. Not published.** No `v0.1.43` tag or GitHub release exists yet;
0.1.42 is still the current public release. This file is what the 0.1.43 notes say when it is published. The
verification table below separates what was run on the candidate tree from what remains a field limitation.

## Build and toolchain

- **Issue #115: builds with Windows SDK 10.0.19041.0 again.** `win_display_state.cpp` used
  `DISPLAYCONFIG_GET_ADVANCED_COLOR_INFO_2` and `DISPLAYCONFIG_SET_HDR_STATE`, which `wingdi.h` only declares from the
  Windows 11 24H2 SDK (10.0.26100). The runtime now declares both requests itself, with the request numbers as
  `UINT32` constants rather than casts into the older SDK's `DISPLAYCONFIG_DEVICE_INFO_TYPE` enum (clang limits that
  enum to [-16, 15], and request 16 is outside it). `static_assert`s pin the header, field offsets, sizes and request
  numbers; the calls cast the pointer back to the SDK's header type. The declarations use local names, so an SDK that
  does define the types does not collide with them.
- **Reproduced, then fixed.** Compiled against 10.0.19041.0, the pre-fix file fails with the reporter's exact errors
  (`unknown type name 'DISPLAYCONFIG_GET_ADVANCED_COLOR_INFO_2'`, `undeclared identifier
  'DISPLAYCONFIG_DEVICE_INFO_GET_ADVANCED_COLOR_INFO_2'`, and the missing `DISPLAYCONFIG_SET_HDR_STATE`). The current
  file compiles against 10.0.19041.0, 10.0.26100.0 and 10.0.28000.0, and a full `fefw.exe` build succeeds with
  10.0.19041.0 and with 10.0.28000.0.
- **HDR compatibility path.** Reading HDR state keeps its fallback: if `GET_ADVANCED_COLOR_INFO_2` is rejected, the
  legacy `GET_ADVANCED_COLOR_INFO` query answers. There is no public legacy setter; `SET_HDR_STATE` exists only on
  Windows 11 24H2 and later, so on older Windows a restore reports the failed request and leaves the display alone
  instead of guessing at a mode change. SDR white level remains read-only (`DISPLAYCONFIG_SDR_WHITE_LEVEL` has no
  setter) and is captured but never written.
- **Issue #116 follow-up: a partly quarantined carried toolchain is detected.** The launcher checks the CMake modules
  and Python runtime in the carried copy, uses a complete installed LLVM or CMake when the carried copy is damaged,
  shows damaged build tools on Overview with a one-click repair, and only blocks Rebuild when the damaged copy would
  actually be used. Every install now records the SHA-256 and size of every required file in a manifest before it stamps
  the piece, and Rebuild re-hashes that set before compiling, so a truncated or same-size substituted tool is named
  instead of being executed (issue #116). `EmblemWeave.exe --verify-tools` reports the state of every carried piece and
  exits non-zero on damage; `--fetch-tools` re-fetches all four pieces even when their stamps are present, which gives
  an install from before the manifest a verified replacement. The Overview keeps a size-only check so its per-frame
  status stays cheap.
- **Release checksums cannot keep a previous build's entries.** `tools/package_release.ps1` now replaces `SHA256SUMS` only after the zip and both manifests are final, using the strict atomic `tools/release_sums.py`. The finalizer refuses a missing or unexpected artifact, duplicate or self-referential entries, a package manifest that disagrees with the bytes on disk, and a stale candidate file. The release workflow uses the same finalizer for the zip, Linux translator and release manifest; `release.ps1` verifies but no longer writes the sums.
- **The carried toolchain now installs from the real archive.** The first end-to-end `--fetch-tools` run on the pinned LLVM 23.1.5 archive failed after downloading and unpacking it: the required-file list named `vcruntime140.dll` and `vcruntime140_1.dll`, which that upstream archive does not contain. The list now matches what the archive ships. A clean fetch downloads 334 MB (LLVM 276,368,249; CMake 46,473,549; Ninja 289,808; Python 11,094,114 bytes), verifies every pinned SHA-256, unpacks 428 MB into `tools`, writes four manifests (344 file entries total) and stamps each piece; `--verify-tools` then exits 0. A CMake/Ninja project configured with the carried CMake and Ninja and compiled and archived with the carried `clang-cl.exe` and `llvm-lib.exe` succeeds. The full engine also builds from the legitimate Fortune's Weave NUP with the carried tools: 603/603 targets, exit 0, Release, NASM x86-64 dav1d assembly enabled.
- **Manifests fail closed.** An empty or truncated manifest used to read as “no recorded hashes”, and a stamp from another archive was ignored by verification. An empty/unsafe manifest, a required file the manifest does not name, and a stale stamp are now damage: `--verify-tools` exits non-zero and the build gate repairs the piece. Manifest paths that contain `..`, a drive prefix or a backslash are refused. A deliberate fault matrix (missing executable, missing header, truncated and same-size-substituted executables, missing/corrupt/empty manifest, stale stamp, missing Python runtime, traversal attempt) returned exit 1 for every case and 0 after restoring the files.
- **MSVC warning flags.** The build passes MSVC its own warning flags instead of clang's, so the clang-only
  `-Wno-unused-parameter` / `-Wno-everything` spellings no longer reach `cl.exe`. dav1d's MSVC options are passed as
  separate arguments.
- **Long Windows environments (carried from the 0.1.43 draft).** The final `fefw.exe` step now receives the
  launcher's `NX_ENV_READY` handshake, so `runtime/scripts/env.cmd` no longer runs `vcvars64.bat` a second time and
  appends a second toolchain to an already long `PATH`. The failure was `The input line is too long`; the regression
  check drives a 7,906-character `PATH` through both paths and the packaging script runs it before packing.

## Stability

- **Issue #79: a save folder directly in the save root is now named and adoptable.** `find_orphan_saves` looked in
  `profiles/`, other account folders and one level below `account/DEFAULT_USER`, but not at a save folder sitting beside
  them. A recovered tree whose chapters live in `<save folder>/<id>/000` therefore showed "no save" while the game
  opened the account folder and booted the prologue. The Saves page now lists that folder as an orphan and offers **Use
  this save**, which copies it into place after backing up the current save. Nothing is moved automatically, and the
  launcher's `backups/` area is not treated as an orphan. A folder named `000` that holds only unrelated files (for
example `readme.txt`) is not offered as a playthrough either: at least one extensionless game slot must be present,
while any extra files in a real save are still counted and shown.
- **Issue #117: the Obelisk Chamber stall.** The stall was a kernel deadlock introduced by `bd90a2a3`, which split the
  wait queues onto separate locks. `block_on_wake` runs the occupancy hooks while its caller holds the mutex, CV or
  address lock, and those hooks take the sync lock; the split therefore created a mutex-to-sync inversion against
  code that takes sync and then enters the kernel. It also reopened the gap between handing a mutex over and queueing
  its waiter, where an unlock loses the wake-up. The freeze reproduced as 236 presented frames followed by a 30-second
  watchdog report, with main blocked in `arbitrate_lock` -> `block_on_wake` and guest threads blocked in
  `wait_process_wide_key` -> `block_on_wake`. `74e7defc` reverts the sharding and `cf09114c` restores the single
  kernel lock for every wait queue and for occupancy; the constraint is documented in the file so it is not split
  again.
- **Live retest.** With the isolated Obelisk Chamber save on the installed single-lock runtime, the chamber loaded,
  the Wolf Obelisk panel opened and backed out, Replay from Any Chapter opened, and the Main Character switch was
  attempted. No 30-second freeze and no watchdog report. The largest hitch across the retests was 646.9 ms during
  initial shader and asset warm-up; post-startup frames were 151.5 ms or less (the latest run: 545.0 ms at startup,
  151.5 ms later). The switch itself was not visually confirmed, because the shoulder, D-pad and mouse attempts all
  activated the panel's focused Replay action. That part of the scenario remains unverified.
- **Media Foundation is loaded only when a movie asks for it.** `mfplat` and `mfreadwrite` are delay-loaded and the
  runtime checks for them at the point a movie opens, so a start-up, a route or a battle does not pull the media stack
  into the process. Unlike the upstream patch, `winhttp` is not linked.
- **Memory lock order.** The write tracker takes its scope before the heap lock, removing a lock-order inversion
  between write tracking and guest heap operations.
- **Movie teardown.** A stream now ends when the player joins its handler, and a stream whose player holds every frame
  and stops no longer keeps the decoder alive.
- **NVN descriptor sets.** The set cache is per-frame by construction, the current array is used when a set is
  rewritten, the frame counter is declared before the cache, and in-flight sets are not overwritten across split
  submissions. Chunk imports stay on the render thread.
- **Texture preparation.** Background data is written in the texture image's own format (#146), a remade image
  publishes its new format and only opaque BC1 is cached, format-forced jobs for new images are ignored, and a BC5
  image is remade when it is rewritten with uncached ASTC content (#177). A live texture gets its image back from the
  finalized set (#174), and block-compressed array levels are copied one layer at a time.
- **GPU pipeline deferral.** Async GPL deferral stays active across hitches (#147) and its frame-seen state is reset
  on shutdown; prewarm waits are timed.
- **Time services.** Shared-memory remapping is held off during writes, clock contexts are refreshed when the host
  clock moves, the steady-clock correction is published in `ContinuousAdjustmentTimePoint`, and the adjustment fields
  match the SDK reader.
- **Audio.** The XAudio2 engine is stopped before voice destruction, start-up no longer opens and closes a probe, and
  device reopens are limited (#44). The AudRen sink remembers a failed open, retries with backoff, caps direct-open
  retries at three, and only retries when the default output endpoint changes.
- **Rendering fixes.** FSR 3 white scenes on AMD with Mesa 26.3.1, the shown-FPS underflow after a swapchain remake,
  borderless instead of windowed on the Radeon 8050S/8060S (#81), smaller VMA blocks on 4-6 GiB video heaps, and the
  frame limiter staying active during loading screens (#151).
- **Menus and input.** L / R tab switching in the F1 menu no longer activates the first control. HDR-only and SDR-only
  Picture controls are hidden according to the current HDR state.
- **Out of memory.** The launcher warns before Play when the process is close to the limit, and the crash report gives
  the out-of-memory cause its own slot instead of folding it into a generic device-lost report.

## Performance

- **Engine port: fefw-recomp 0.2.12-0.2.13 (PR #109).** Replay hot-path work (pool caches, inline output snapshot,
  set/viewport/pipeline fast paths), cheaper bind bodies and identity swizzles, batched counter and event writes,
  narrower transfer barriers, cached TSR-jittered camera UBOs, lazy dummy views, precomputed program-layout texture
  lists, and sequential write-watch fault coalescing.
- **Residency.** Host-RAM demotion starts at 92 percent and never holds restores (#114); the restore budget has a
  test, and the demotion log line says what it counts.
- **Atomics.** The runtime is built with `-mcx16`, so `std::atomic` operations are inlined instead of calling a
  helper.
- **Find Units (#76).** The scan is parallel with cancellation, progress and a bounded worker count. Cancellation, the 30-second deadline and target loss are now checked after every read as well as before it; a buffer returned after cancellation is discarded and partial results are rejected by `scan_outcome`. A read already inside `ReadProcessMemory` cannot be interrupted by those checks, and the UI says so. The API limitation and the helper-process option are documented in `docs/audits/FIND_UNITS_BLOCKING_READ.md`.
- **Launcher scans.** Mods-page filesystem scans moved off the UI thread (#114), and the Graphics page caches its
  probes with a 30-second TTL and background rescans (#59).
- **Ultrawide.** Fortune's Weave draws ultrawide outputs wider than 3840 at their own size, and outputs above 3840
  raise the game's own sizes at the VI answer (PRs #111/#112).

## Launcher

- **Mods page.** A mod's settings file can be opened; GameBanana pages can be checked for updates and updated in
  place; several installs run at once with their questions queued; builds for different platforms and mutually
  exclusive variants are offered and only one is switched on. Mods are classified by content, and the Trinity page is
  folded into Mods.
- **Trinity.** External `Trinity.dll` is supported for code mods, with a version-safety check, and the launcher bundles
  Trinity 0.2.0 with a native page describing it.
- **RecompLauncher.** `recomplauncher.json`, `--game <path>`, and the RecompLauncher badge are supported; updates are
  left to RecompLauncher when it starts EmblemWeave.
- **Update integrity.** Downloaded updates are verified against the published SHA-256 before they are applied.
- **Report An Issue.** The launcher's own troubleshooter prepares a structured GitHub issue and attachments for the
  user to submit. It does not upload anything by itself, and this release contains no remote reporting endpoint.
- **Saves.** A slot moved back under its backup name is recovered before the game starts, and the existing
  reconciliation, adoption and damaged-autosave quarantine behaviour is unchanged.
- **Display.** The launcher's 21:9 setting now sets the wide output the F1 menu uses, and the wide panels use their
  own widths.

## Compatibility and input

- SDL 3.4.20.
- A Bluetooth DualSense that SDL reports as wired is recognised for haptics.
- Xbox Direct haptics actually drive the pad; RenHDrum 0.6.0 adds advanced controller haptics, with the credit added
  to the About page.
- A controller that SDL misses at start is picked up and the reason is logged.

## Known issues

The 0.1.42 field limitations still apply: #37 multi-hour stability, #41 device loss on 16 GB shared-memory hardware,
#76 in-game Find Units frame time, #77 the reporter's damaged save and #78 HDR state restoration. AV1 playback is now
verified through both the assembled dav1d decoder and FFmpeg/D3D11VA; Opus decoding, seeking, pause/resume and a
measured A/V drift remain unverified (#70/#75). The #117 character switch is implemented and covered by the kernel
suite, but the in-game switch was not visually confirmed. HDR state changes were not exercised live during this pass
because doing so changes the display.
