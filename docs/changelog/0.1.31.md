# EmblemWeave 0.1.31

> A `.nx` plays from the archive again, and a build folder that lost its compiler starts over instead of failing

## `.nx` is read where it is

`0.1.27` copied a `.nx` RomFS out to disk because the engine could no longer read NXFormat's container. That copy is gone: the engine
has its reader back (`runtime/src/loader/nx.cpp`), so a RomFS read is a block read of the archive, zstd-decoded and integrity
checked when the game asks for it, and the 29 GB file is never duplicated. The launcher hands the archive over as it is, reads the
shader archives straight out of it, and the Setup page says "read in place" instead of "written out once".

Two things had to move with it. zstd is now fetched for every runtime build rather than inside the graphics shell, because the
loader needs it. And the prompt font loader reads `/Font/...` through the engine's own RomFS image, so the extension fonts are found
whether the data is a folder, a `.nup` or a `.nx`.

## Build: a cache reset no longer turns clang-cl into clang++

`0.1.27` reported `unknown argument: '-clang:-fmacro-prefix-map=...'` and `no such file or directory: '/W3'`. The log shows why:
part-way through the configure CMake announces "You have changed variables that require your cache to be deleted", configures again
without the flags it was given, and the build continues with `clang.exe` (the GNU driver, which rejects `/W3`) in Debug.

Now the compilers and the resource compiler go into the cache with their types (`-DCMAKE_C_COMPILER:FILEPATH=...`), the same values
go into `CC`, `CXX` and `RC` so they survive that announcement, and after the configure the script reads `CMakeCache.txt` and checks
what the build actually got. A folder configured with another compiler or another configuration is started over with a line saying
so, instead of failing three minutes later inside dav1d.

## Verified

- The engine ran against the real 28.9 GB `.nx`: `RomFS image from <file>: 252693 files, 21467 directories, 29107027700 bytes of
  data`, 25 seconds headless, exit 0, the extension fonts decoded (`__nintendo_ext_003.bffnt.zst: 1024x1024 x1 BC4 sheet ...`).
- A launcher build with the `.nx` as Game data: ExeFS copied out of the archive, six modules compiled, `fefw.exe` built.
- `cargo build --release`, `cargo test -p emblemweave` (119 passed).
- Not verified: the `-clang:` failure itself could not be reproduced on this PC (the cache reset never happened here), so what is
  tested is that a fresh configure ends with `clang-cl` in `Release` and that a folder with the wrong cache entry is restarted
  instead of used.
- Not done yet: `.xci`. It needs an HFS0/cartridge reader on top of the `.nsp` NCA path, and there is no `.xci` here to test it
  against, so it is not in this release rather than shipped blind.
