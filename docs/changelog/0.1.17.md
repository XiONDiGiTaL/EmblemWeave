# EmblemWeave 0.1.17

> The engine is Obersteinn's preserved 0.2.0 tree, it builds from an empty folder on this PC, and the game was played to the menu and back to check it

## What's new

- **The engine is the tree Obersteinn preserved, not an older one.** `engine/fefw-recomp` was replaced wholesale with the
  0.2.0 tree: haptics through the vendored `renHDrum.dll`, ASTC transcoding on the GPU, residency management, the Vulkan
  layer filter, the render status page, the per-CPU game variants and the per-block shader journal the build keeps. 0.1.16
  ran an earlier engine, and [docs/UPSTREAM.md](../../docs/UPSTREAM.md) now says plainly that the audit behind it compared
  build tools rather than runtimes, which is how a tree that was not the final one passed.
- **The Windows resource step no longer hangs.** On this PC the SDK's `rc.exe` sat at zero CPU on the preprocessed
  `fefw.rc` for fifteen minutes, having written its temp files and never returned, and the build stopped at 147 of 150
  targets. `game-build/fefw/CMakeLists.txt` now gives the job to `llvm-rc`, the resource compiler that ships beside the
  `clang-cl` this build already requires, and replaces a cache that still names `rc.exe`. The same file compiles in
  milliseconds.
- **A failed build names the failure, not a warning above it.** `env.cmd` probes for Visual Studio through `vswhere`, and
  when that probe misses it prints `'vswhere.exe' is not recognized` and carries on with the toolchain already on `PATH`.
  The launcher searched the whole log for a missing program, found that line, and told the player to install `vswhere`
  when the build had in fact died at the resource step. It now looks at the reason the step gave first, and only then at
  the wider log.

## Verified by building and playing it

The build was run from an empty build folder on this PC, and then the game was played:

- `prepare_exefs.py` copied the ExeFS out of the dump; `build_game.cmd fefw` lifted and compiled the six libraries
  (89 710 functions, 6 715 398 instructions, none left untranslated); `build_fefw.ps1` configured with `clang-cl` and
  `llvm-rc` and built 585 of 585 targets into `fefw.exe`; the corpus was extracted from the RomFS and all 12 088 shader
  blocks are translated, with the 79 blocks beyond the translator listed in `results.tsv`; the launcher wrote
  `%APPDATA%\EmblemWeave\play\fefw.ini`.
- The game then ran from that folder: the title screen at 60 fps, **Continue** loading the save in use (Part I,
  Theodora's Path, chapter 4, *Unlikely Alliances*, Dagson), the hub area rendered with its minimap and objective line,
  the character walking forward when `W` was held, **Tab** opening the in-game menu, and **F1** opening the engine's
  settings overlay. 47 to 68 fps through the visit, texture uploads and ASTC transcodes settling as areas loaded, and no
  errors in `fefw.log`.
- The keyboard needs a held key on this engine. The menu moves on `1` `2` `3` `4` (the D-pad), not the arrow keys, which
  drive the right stick; a key pressed and released inside one frame is not seen at all, which is why a quick synthetic
  tap did nothing at the title screen.

## Under the hood

- The build copies `renhdrum.dll` beside `fefw.exe` after linking, the only folder `haptic.cpp` loads it from, so rumble
  arrives through the game's own haptic calls instead of the standard two-motor fallback.
- The Controls page writes `[pad] haptic` and `[pad] haptic_strength`, the keys this engine reads, and still reads the
  older `rumble` and `rumble_scale` from files written before them.
- The shader step calls the harness without `--only-missing`: this tree keeps a per-block journal and resumes from it, so
  the flag the previous tree needed is gone.
- Eight JSON files this tree needs to build are in the repository even though its `.gitignore` excludes `*.json`, among
  them `dump_hashes.json` and the two test oracles.
