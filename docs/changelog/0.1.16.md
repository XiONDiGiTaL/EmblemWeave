# EmblemWeave 0.1.16

> The release that finds its own toolchain, ships a zip that builds, and stops calling a half-built shader cache translated

## What's new

- **The toolchain is found, not assumed.** `vswhere` lists every Visual Studio install with the x64 C++ tools, the newest
  one that is 2022 or newer is chosen, and the MSVC toolset and Windows SDK are read from the environment `vcvars64.bat`
  itself produces. That last part matters: on this PC the SDK is on `D:` and `C:\Program Files (x86)\Windows Kits\10`
  holds nothing but metadata, which is exactly the case a fixed path gets wrong.
- **Every build step gets the same environment.** `vcvars64.bat` runs once; its `INCLUDE`, `LIB`, `PATH` and `VCINSTALLDIR`
  are passed to every child process, and an inherited `CC`, `CXX`, `CL`, `INCLUDE`, `LIB` or `CMAKE_*_COMPILER` is dropped
  first, with a log line saying so. A shell that had run another `vcvars` can no longer send the build to headers nobody
  checked.
- **One file is compiled and linked before the recompile starts.** It includes `<bit>`, `<string>`, `<vector>` and
  `windows.h`, so a missing C++ workload, an old toolset, half an installed SDK or a `LIB` from another install fails in a
  second, naming the compiler and the error. `EmblemWeave.exe --check-toolchain` runs the same report and probe without a
  window: 0 ready, 1 a piece is missing or too old, 2 it cannot compile.
- **A build folder is only reused by the toolchain that made it.** `CMakeCache.txt` is read before configuring: a cache
  naming another compiler, generator or toolchain file is cleared, and the log says which value disagreed.
- **Cancelling stops the tree.** `cmd`, `cmake`, `ninja` and a core's worth of `clang-cl` are stopped together, so nothing
  keeps writing into the build folder after the job is gone. Ninja re-runs an edge it never recorded, so a half-written
  object is not treated as finished.
- **One build at a time.** `work\build\.build.lock` names the process holding the engine folder; a second build refuses
  with that process id, and a lock left by a killed launcher is recognised and replaced.

## The black screen, fixed

- **Black picture with the sound playing, fixed.** Players running from a `.nup` got a window that stayed black
  while the music played (issues #12 and #15). The game was reading its assets from the package as it should; the
  shaders were the problem. The shader corpus is built by walking the RomFS folder, and a `.nup` is a file, so the
  walk found nothing and the corpus came out as only the shaders inside `main`: 151 cache records on the reporter's
  machine, where the game needs 12 088 blocks. Every scene program then had no translated shader, every draw was
  skipped, and the present pass copied an untouched texture to the window 60 times a second. **Build the game** now
  copies the shader archives (`*.bfsha`, `*.ptcl`, `*.arc`, `*.sarc`, `*.bnsh`, about 1.4 GiB) out of the package
  once, builds the corpus from that folder, and remembers which folder each corpus came from, so one built from a
  path that is not it is rebuilt instead of reused.
- **A half-translated cache is repaired, not called translated.** The build used to skip the shader step when any
  `.spv` existed. It now compares what the corpus expects (`corpus/unique.tsv`) with what the translator reported
  (`spirv/results.tsv`, written only when a run finishes), translates just the missing blocks with the harness's new
  `--only-missing`, and merges each run's report instead of replacing it. A cache with a few files and no
  `results.tsv` is a translation that was interrupted, and that is what it reports now.
- **The engine says which GPU it picked, and when a frame reached the screen.** The GPU lines carry vendor and
  device ID and the driver version decoded from Vulkan's packed form; `first frame presented: 1280x720, format 44,
  present mode immediate, frame 1` is logged once, at the present that succeeded. A present that failed is no longer
  counted as a frame on the display, `VK_ERROR_DEVICE_LOST` is named on acquire, submit and present, and the out of
  date and surface lost results say what they mean.
- **One error instead of 598 warnings.** A program whose shader was never translated used to log a warning per
  program: 598 of them in the reporters' logs, each true, none of them saying what they added up to. The first eight
  are still listed by block hash, then the engine states the consequence once: every draw belonging to them is
  skipped, the window shows only what the last clear left, and the SPIR-V folder it looked in is named. The shader
  cache now records its folder even when `results.tsv` is missing, which is the case that printed an empty path.
- **A rendering test that reads the picture back.** The graphics tests gained
  `presents_a_known_colour_and_reports_the_first_frame`: a 320x180 window, eight frames, a screenshot at the fifth,
  and then the pixels themselves, because a present that returns `VK_SUCCESS` is not a frame on the screen. It fails
  on `presents != 8`, on a failed present, on device loss, on a validation error, and on a mean channel of 2 or less
  (the scene clears to about 13, 20, 36), so a black window fails it. It runs without the game, like the rest of
  `nxrt_gfx_tests`.

## The zip, and the build from it

- **The zip is written entry by entry, and checked before it is published.** The old packaging handed the folder to
  a compressor, which is how a Windows build produces names with backslashes and, on Linux, one flat pile of files.
  `tools/package_release.ps1` now builds every entry with forward slashes inside the same `EmblemWeave-vX.Y.Z/`
  folder every release has extracted to, writes the folder entries, keeps the executable bit, and runs the new
  `tools/verify_archive.py` against the file it just wrote. The verifier refuses
  absolute paths, drive letters, `..`, `./`, backslashes, control characters and case-colliding duplicates, checks
  that the files the launcher reads are at their paths, and with `--extract` unpacks the archive and checks nothing
  landed outside its folder. `tools/release.ps1` runs it again over the assets and compares their hashes with the
  manifest before `gh release`. Verified: 1287 files in 131 folders, no backslashes, no absolute entry, and the
  same tree from `unzip` and from Python's `zipfile` under Ubuntu; the translator tarball extracts with
  `-rwxr-xr-x` and its ELF binary prints its usage. One real bug came out of it: `docs/PACKAGE.md` was landing in
  the zip's root, not in `docs/`.
- **Builds from the zip get past CMake again.** The release package excluded every folder named `third_party`,
  which took `runtime/third_party` with it: dav1d, FSR 1, NIS, Streamline and the ffx API. Every build from a
  download then stopped at `add_subdirectory given source .../runtime/cmake/../third_party/dav1d which is not an
  existing directory`, and downloading dav1d by hand did not help unless it landed exactly there (issues #16 and
  #17). The two fetched trees (`tools/textures/third_party`, `tools/shaders/third_party`) are now named
  individually and the runtime's own is shipped, so the zip goes from 1287 to 1480 files. The verifier requires
  `runtime/third_party/dav1d/CMakeLists.txt` from now on, and the engine's `media_deps.cmake` builds without the
  AV1 movie decoder, with a status line, if a tree genuinely lacks it, instead of failing the configure. The
  packaging step now also extracts its own zip and runs the engine's CMake configure from the extracted tree before
  publishing, so a package whose build cannot start fails on the machine that made it instead of on the player's.
  The full build from a zip was run here: 549 of 549 targets, `fefw.exe` linked, dav1d compiled from the download.

## The launcher: saves, vibration, graphics, and Linux

- **The launcher compiles for Linux, and says so before it refuses.** Every operating-system fact now comes from
  one module (`platform.rs`): whether the game is running, whether this system may install build tools, whether it
  can build the game, where the launcher's data lives, and what the platform is called. Off Windows the installer
  and the build refuse with a sentence naming the platform and pointing at [docs/LINUX.md](../LINUX.md), instead of
  running `winget` and a `vcvars64.bat` that are not there. `cargo check -p emblemweave --target
  x86_64-unknown-linux-gnu` exits 0, which is a compile and not a claim that the game plays there: Linux, SteamOS
  and the Deck have a documented plan with the phases that were actually run marked, and native Linux support is
  not advertised. [docs/PLATFORMS.md](../PLATFORMS.md) is the audit of the 69 files that include `<windows.h>`,
  the 28 `Command::new` call sites and what each one needs on another system.
- **Saves load, and profiles can be renamed and copied.** Loading a profile wrote it into the first account folder
  by name, and the engine names that folder after the save's owner: with more than one present (its built-in user,
  a console user id, a folder an earlier import left empty), the profile went where the game never looks, which is
  why loading appeared to do nothing. The launcher now reads and writes the account folder the game last wrote. The
  Slots list shows each slot's size and the save it belongs to, and moves a slot to `backups/` so the game offers
  a new game there again. Profiles take a name and can be renamed (the folder moves) or copied (a branch of the
  story), and Remove still moves rather than deletes.
- **Vibration reaches the game.** The Controls page's Vibration slider was kept in the launcher's own config and
  never written where the engine reads it, so the pad never shook (issue report: it did on the gold disc). Rumble
  is now a switch (`[pad] rumble`) and a strength (`[pad] rumble_scale`, 0 to 100 %), read from and written to the
  game's `controls.ini` like the dead zones, seeded from the launcher's saved value when the file has none.
- **A graphics menu with the settings the engine actually has.** The Rendering section gained the temporal
  upscalers' quality preset, the game's own scene scale, frame generation (DLSS or FSR 3), what replaces the
  game's console DLSS calls (TAAU, DLSS, FSR 3 or bilinear), texture compression quality and the GPU choice. Each
  one is written to the engine's own keys (`[upscale] quality`, `scene_scale`, `[dlss] frame_gen`, `upscaler`,
  `[display] astc_quality`, `[gfx] gpu`), and a change made in the game's F1 menu is taken back onto the page.
- **Shader compilation has a CPU dial.** While a new area loads, the engine compiles shader parts and whole
  pipelines on background threads; its default is `min(4, cpus / 6)`, below normal priority, in Windows'
  efficiency mode, which on a 24-thread laptop is still four threads at the top of the boost table (reported: CPU
  clock at 6 GHz while shaders compiled). The new Shader compilation section caps that thread count and sets its
  priority to below normal, normal or idle, and can switch the efficiency mode off; the values go to `[nvn]
  gpl_threads`, `compile_priority` and `compile_eco`, and are left alone at Automatic.

## One place for requirements

- **A registry, not scattered checks.** `apps/emblemweave/src/deps.rs` holds each dependency once: its name, minimum
  version, how it is detected, the line that installs it, whether it is mandatory or optional, and the stage that needs it.
  The pre-build check, the installer, the Requirements page, `--print-requirements` and the tables in the README and
  `docs/TROUBLESHOOTING.md` all read that one list, so they cannot disagree. A test compares both marked tables with the
  generated text and fails when the registry changes and the docs do not.
- **A Requirements page.** **System > Requirements** lists every dependency with its status (installed, too old, missing,
  not needed), the version and path that answered, the stage that needs it, and the install line for the ones that do not
  pass, each with its own Install button. One button runs everything that is missing, and **Check again** re-runs every
  check in place: no launcher restart, because the checks read the folders a fresh install lands in.
- **Bundled is not the same as from source.** The registry separates the shader translator, the .NET runtime and the .NET
  SDK. With a bundled translator the SDK and runtime rows read "Not needed" and are never installed or asked for; only a
  build that compiles the translator from source wants the SDK. The translator row says which case this release is in.
- **Checks use the build's environment, not the launcher's.** Detection searches the same `PATH` the build gets (the
  launcher's tool folders, then what `vcvars64.bat` sets), so a tool the build would not find cannot pass the check, and
  the Windows SDK is read from the variables `vcvars` produces: on this PC it is `10.0.28000.0` on `D:`, where a scan of
  `C:\Program Files (x86)` finds nothing.
- **Python is asked, not guessed.** `python`, `py -3`, `python3` and the engine's own virtual environment are each run, the
  newest that answers is reported with the file that answered, and `zbic` is imported separately in every one of them, so
  a `python` and a `py` that point at different installs cannot hide a missing package.
- **NASM is checked at last.** The dav1d assembly steps need it; the old tool list did not mention it, so a build without
  NASM stopped several minutes in with a compiler message about an assembler.
- **A failure names all four things.** Every blocking row gives the component, the minimum version, what was detected
  (including "not found") and the install line, in the installer output, on the page and in `--check-toolchain`.

## Fixed in the build scripts

- `nx_env.cmd` and `env.cmd` clear `CC`, `CXX`, `CL`, `INCLUDE`, `LIB` and `LIBPATH` before calling `vcvars`, then stop
  with a named exit code when `vcvars64.bat` is missing, when it sets no `INCLUDE` (the C++ workload is missing), when
  `clang-cl` or `lld-link` is absent, or when CMake or Ninja is not on `PATH`. None of them puts a path in parentheses
  inside an `if ( … )` block any more: a value like `Program Files (x86)` ended the block early and turned the rest of the
  script into stray commands, which is what `". was unexpected at this time."` was.
- `build_game.cmd` and `build_fefw.ps1` name the compiler by full path, configure and build as separate steps, and say
  which one failed instead of returning a bare exit code.
- The texture fetch downloads to `.part`, checks the pinned SHA-256, and moves the file into place only then; clones go to
  `.partial` and are moved after the files the build opens are there; a folder that exists without them is discarded and
  fetched again; four attempts with backoff, and a lock file so two builds cannot fetch into the same tree.
- The Ryujinx checkout is cloned into `work\refs\ryubing.partial` and moved after the pinned revision is checked out and
  its projects are present. Previously a clone interrupted halfway left `.git` behind, which passed the "is it there"
  test and failed later inside `dotnet`.
- Texture sources are checked by file, not by folder: `astc-encoder`, `bc7enc_rdo` and `ispc.exe` each have to be there,
  so a half-finished fetch no longer counts as fetched.

## Verification

`cargo test -p emblemweave`: 116 tests, 10 of them ignored because they need a game dump. The registry's tests keep both
docs tables equal to the generated text and treat a bundled translator as "no .NET SDK"; the rest cover the new parsers
(`vcvars` `set` dumps, `clang-cl --version`, CMake cache facts and mismatch rules), numeric toolset ordering, the build
lock (a stale lock is taken over, a held one is dropped on release), the texture check by file, clearing a cache on
disk, the pad's rumble keys and the account folder a profile loads into.

On this PC, with Visual Studio 2026 Build Tools 18.10 and LLVM 23.1.5: `--check-toolchain` lists all fourteen
requirements as found (Visual Studio 18.10 with MSVC 14.51, SDK `10.0.28000.0` from `D:\Windows Kits\10`, clang-cl
23.1.5 beside lld-link, CMake 4.4.4, Ninja 1.13.2, NASM 3.02, Git, PowerShell 7.7, uv 0.13.6, .NET SDK 10.0.404, the
translator built here, Python 3.14.7 through `py` with `zbic` in the engine's virtual environment, and clang as the C
compiler), then compiles and links its probe and exits 0. `--print-requirements` prints the table the two docs carry. With `CC`, `CXX`, `INCLUDE`, `LIB`
and `VCINSTALLDIR` set to bogus values it lists each one as ignored and still passes. `nx_env.cmd` and `env.cmd` exit 0
and print the tool versions they found; `build_game.cmd fefw` and `build_fefw.ps1 -Target fefw_obj` configure and report
`ninja: no work to do` on the existing artifacts, so both run with the new environment and reuse what was built.

The release assets were checked from both sides: `tools/verify_archive.py` extracts the zip and finds 1480 files in
161 folders with `/` names, and it does the same under Ubuntu 26.04 with `unzip` and with Python's `zipfile`; the
translator tarball extracts with `-rwxr-xr-x` and its ELF runs. **Build the game** was run from the extracted zip on
a clean tree (only the lifted libraries added, as the launcher would): 549 of 549 targets, `fefw.exe` linked, dav1d
compiled from the download. The new packaging step configured that same zip before publishing, and the same command
against a deliberately broken tree exits 1, which is what stops a release.

Not tested here: a machine with an old Visual Studio, a missing SDK or a broken download. Those paths are covered by the
unit tests of their parsing and by the code that produces the messages, not by a run.

## Still required

Visual Studio 2022 Build Tools with "Desktop development with C++", LLVM 23 or newer, CMake 3.25 or newer, Ninja, NASM,
Git, PowerShell 7, uv and a Windows 10/11 SDK. The Requirements page and `--check-toolchain` are the list; both read the
registry above. The .NET 10 SDK is not needed when the zip carries the translator. Steam Deck: the game runs under
Proton, the build does not; `docs/STEAMDECK.md`.
