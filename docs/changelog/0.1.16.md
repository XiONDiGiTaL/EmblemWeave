# EmblemWeave 0.1.16

> The build checks its own toolchain before it compiles anything, and repairs what it can instead of failing later

## What's new

- **The toolchain is found, not assumed.** `vswhere` lists every Visual Studio install with the x64 C++ tools, the newest
  one that is 2022 or newer is chosen, and the MSVC toolset and Windows SDK are read from the environment `vcvars64.bat`
  itself produces. That last part matters: on this PC the SDK is on `D:` and `C:\Program Files (x86)\Windows Kits\10`
  holds nothing but metadata, which is exactly the case a fixed path gets wrong.
- **Every build step gets the same environment.** `vcvars64.bat` runs once; its `INCLUDE`, `LIB`, `PATH` and `VCINSTALLDIR`
  are passed to every child process, and an inherited `CC`, `CXX`, `CL`, `INCLUDE`, `LIB` or `CMAKE_*_COMPILER` is dropped
  first, with a log line saying so. A shell that had run another `vcvars` can no longer send the build to headers nobody
  checked.
- **One file is compiled and linked before the recompile starts.** It includes `<bit>`, `<string>`, `<vector>` and
  `windows.h`, so a missing C++ workload, an old toolset, half an installed SDK or a `LIB` from another install fails in a
  second, naming the compiler and the error. `EmblemWeave.exe --check-toolchain` runs the same report and probe without a
  window: 0 ready, 1 a piece is missing or too old, 2 it cannot compile.
- **A build folder is only reused by the toolchain that made it.** `CMakeCache.txt` is read before configuring: a cache
  naming another compiler, generator or toolchain file is cleared, and the log says which value disagreed.
- **Cancelling stops the tree.** `cmd`, `cmake`, `ninja` and a core's worth of `clang-cl` are stopped together, so nothing
  keeps writing into the build folder after the job is gone. Ninja re-runs an edge it never recorded, so a half-written
  object is not treated as finished.
- **One build at a time.** `work\build\.build.lock` names the process holding the engine folder; a second build refuses
  with that process id, and a lock left by a killed launcher is recognised and replaced.

## One place for requirements

- **A registry, not scattered checks.** `apps/emblemweave/src/deps.rs` holds each dependency once: its name, minimum
  version, how it is detected, the line that installs it, whether it is mandatory or optional, and the stage that needs it.
  The pre-build check, the installer, the Requirements page, `--print-requirements` and the tables in the README and
  `docs/TROUBLESHOOTING.md` all read that one list, so they cannot disagree. A test compares both marked tables with the
  generated text and fails when the registry changes and the docs do not.
- **A Requirements page.** **System > Requirements** lists every dependency with its status (installed, too old, missing,
  not needed), the version and path that answered, the stage that needs it, and the install line for the ones that do not
  pass, each with its own Install button. One button runs everything that is missing, and **Check again** re-runs every
  check in place: no launcher restart, because the checks read the folders a fresh install lands in.
- **Bundled is not the same as from source.** The registry separates the shader translator, the .NET runtime and the .NET
  SDK. With a bundled translator the SDK and runtime rows read "Not needed" and are never installed or asked for; only a
  build that compiles the translator from source wants the SDK. The translator row says which case this release is in.
- **Checks use the build's environment, not the launcher's.** Detection searches the same `PATH` the build gets (the
  launcher's tool folders, then what `vcvars64.bat` sets), so a tool the build would not find cannot pass the check, and
  the Windows SDK is read from the variables `vcvars` produces: on this PC it is `10.0.28000.0` on `D:`, where a scan of
  `C:\Program Files (x86)` finds nothing.
- **Python is asked, not guessed.** `python`, `py -3`, `python3` and the engine's own virtual environment are each run, the
  newest that answers is reported with the file that answered, and `zbic` is imported separately in every one of them, so
  a `python` and a `py` that point at different installs cannot hide a missing package.
- **NASM is checked at last.** The dav1d assembly steps need it; the old tool list did not mention it, so a build without
  NASM stopped several minutes in with a compiler message about an assembler.
- **A failure names all four things.** Every blocking row gives the component, the minimum version, what was detected
  (including "not found") and the install line, in the installer output, on the page and in `--check-toolchain`.

## Fixed in the build scripts

- `nx_env.cmd` and `env.cmd` clear `CC`, `CXX`, `CL`, `INCLUDE`, `LIB` and `LIBPATH` before calling `vcvars`, then stop
  with a named exit code when `vcvars64.bat` is missing, when it sets no `INCLUDE` (the C++ workload is missing), when
  `clang-cl` or `lld-link` is absent, or when CMake or Ninja is not on `PATH`. None of them puts a path in parentheses
  inside an `if ( … )` block any more: a value like `Program Files (x86)` ended the block early and turned the rest of the
  script into stray commands, which is what `". was unexpected at this time."` was.
- `build_game.cmd` and `build_fefw.ps1` name the compiler by full path, configure and build as separate steps, and say
  which one failed instead of returning a bare exit code.
- The texture fetch downloads to `.part`, checks the pinned SHA-256, and moves the file into place only then; clones go to
  `.partial` and are moved after the files the build opens are there; a folder that exists without them is discarded and
  fetched again; four attempts with backoff, and a lock file so two builds cannot fetch into the same tree.
- The Ryujinx checkout is cloned into `work\refs\ryubing.partial` and moved after the pinned revision is checked out and
  its projects are present. Previously a clone interrupted halfway left `.git` behind, which passed the "is it there"
  test and failed later inside `dotnet`.
- Texture sources are checked by file, not by folder: `astc-encoder`, `bc7enc_rdo` and `ispc.exe` each have to be there,
  so a half-finished fetch no longer counts as fetched.

## Verification

`cargo test -p emblemweave`: 109 tests, including the registry's (both docs tables equal the generated text, a
bundled translator removes the .NET SDK requirement, install lines are runnable and deduplicated, versions compare by
number and not by text), and the new parsers (`vcvars` `set` dumps, `clang-cl --version`, CMake
cache facts and mismatch rules), numeric toolset ordering, the build lock (a stale lock is taken over, a held one is
dropped on release), the texture check by file, and clearing a cache on disk.

On this PC, with Visual Studio 2026 Build Tools 18.10 and LLVM 23.1.5: `--check-toolchain` lists all fourteen
requirements as found (Visual Studio 18.10 with MSVC 14.51, SDK `10.0.28000.0` from `D:\Windows Kits\10`, clang-cl
23.1.5 beside lld-link, CMake 4.4.4, Ninja 1.13.2, NASM 3.02, Git, PowerShell 7.7, uv 0.13.6, .NET SDK 10.0.404, the
translator built here, Python 3.14.7 through `py` with `zbic` in the engine's virtual environment, and clang as the C
compiler), then compiles and links its probe and exits 0. `--print-requirements` prints the table the two docs carry. With `CC`, `CXX`, `INCLUDE`, `LIB`
and `VCINSTALLDIR` set to bogus values it lists each one as ignored and still passes. `nx_env.cmd` and `env.cmd` exit 0
and print the tool versions they found; `build_game.cmd fefw` and `build_fefw.ps1 -Target fefw_obj` configure and report
`ninja: no work to do` on the existing artifacts, so both run with the new environment and reuse what was built.

Not tested here: a machine with an old Visual Studio, a missing SDK or a broken download. Those paths are covered by the
unit tests of their parsing and by the code that produces the messages, not by a run.

## Still required

Visual Studio 2022 Build Tools with "Desktop development with C++", LLVM 23 or newer, CMake 3.25 or newer, Ninja, NASM,
Git, PowerShell 7, uv and a Windows 10/11 SDK. The Requirements page and `--check-toolchain` are the list; both read the
registry above. The .NET 10 SDK is not needed when the zip carries the translator. Steam Deck: the game runs under
Proton, the build does not; `docs/STEAMDECK.md`.
