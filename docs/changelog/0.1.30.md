# EmblemWeave 0.1.30

> NASM joined the optional list; the engine builds without it

The requirements table is down to six rows: Visual Studio C++ tools with the Windows SDK, LLVM, CMake, Ninja and Python. That is
close to what fefw-recomp asked for on its own, and every tool that left has a reason written next to it on the Requirements page.

## NASM

The engine's `runtime\third_party\dav1d\CMakeLists.txt` already turns `NXRT_DAV1D_ASM` off when `nasm` is not found, so a PC
without NASM never had a build failure waiting for it, only a slower AV1 decoder. The launcher no longer stops before that point: it
builds, and the build log says the decoder is C only. Install NASM when 1440p cutscene movies matter; skip it when they do not.

## What still has to be there, and why

- **Python** runs `tools\nso\prepare_exefs.py`, which writes an uncompressed copy of `main`. FEFW's `main` is ZBIC-compressed
  (NSO flag bit 7), a Nintendo zstd variant whose FSE tables need the `zbic` package; the lift and the runtime both read only the
  plain copy, so this step cannot go until something in the build can decode ZBIC without that package.
- **LLVM, CMake and Ninja** are the compilers and generators of the recompiled game code and of `fefw.exe`.
- **Visual Studio C++ tools with the Windows SDK** supply the libraries and headers the runtime links against.

## Verified

- `nxrt_dav1d` built with `-DNXRT_DAV1D_ASM=OFF`: 41 steps to `Linking C static library third_party\dav1d\nxrt_dav1d.lib`,
  no NASM invocation in the log.
- A full engine build with NASM present is unchanged from 0.1.29, including the AV1 assembly.
- `cargo build --release`, `cargo test -p emblemweave` (119 passed), README and TROUBLESHOOTING tables regenerated from
  `--print-requirements`.
- Not checked: a whole `fefw.exe` build on a PC without NASM (only the decoder target was built that way here), and movie playback
  with the C-only decoder.
