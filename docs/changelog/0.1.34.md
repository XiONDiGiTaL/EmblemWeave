# EmblemWeave 0.1.34

> Saves load again, shader compilation stops pinning every core, vibration can be tested, and the launcher has a modern dashboard, a carousel and its own window shell. A new Troubleshooter turns a failure into an attachable report. Fresh releases are portable by default. CMake prereleases are found, a reused old engine is caught before Play, and upscaler files are found inside extracted SDKs.

## A freeze report now carries memory evidence (#37)

The report attached to #37 ends at `FREEZE: no frame tick for 10.0 s (frame count 0)`: the main thread stopped while opening
a batch of `/Sound/Data/Voice/*.elf.zst` files, the render thread was waiting, and no frame had been presented. It carries
no allocation figure, so it cannot distinguish an exhausted heap from an audio stall, a driver wait or a very long decode.

The engine watchdog now records, beside the existing thread and call-site section, the process working set and peak, the
private commit, the pagefile commit, system RAM and commit, the runtime's guarded-heap footprint and limit, and the
presented-frame count. A freeze from this release will show whether memory was actually exhausted at the moment of the
stall. The issue is not closed here and no leak is claimed fixed: this is the measurement needed to prove or reject the
report's hypothesis.

## A Troubleshooter that produces a report

**System > Troubleshooter** reuses the checks the rest of the launcher already runs instead of adding a second detection
system. It shows the game-data result, the build-tool and CMake checks, the last build and run outcome, the save folder and
the recent log, each with the same status the other pages use. Common fixes are grouped by symptom: missing tools, a
package the engine refuses, a black screen, a build that stopped, and a save that will not load.

**Create report** writes a timestamped folder and `.zip` under `data/reports` (or the profile folder in a non-portable
install) containing `config.json`, the job logs, the game log, any `fefw_freeze.txt` or crash report, and a short
`report.txt` that names the version, build, Windows build and the checks' results. The page shows the exact folder and
file, opens either one, and builds a prefilled GitHub issue URL with the version and a short description. The zip is
written by the launcher itself, so it is a real zip on every PC; nothing is uploaded until you attach it. Attach it to
the issue yourself, where you can read it first.

The safe repairs on the page are the ones the launcher can already perform: rebuild the game, reset graphics to safe
defaults, open the log and report folders. Nothing on the page deletes saves or game data.

## The launcher has its own shell

The native Windows title bar is gone. A slim top strip carries the crest, the current page, the version and build revision,
and its own minimise, maximise and close buttons; dragging it moves the window, double-clicking maximises, and all four
edges and corners resize it. The strip uses the same palette, type and hairline as the rest of the launcher, so the window
no longer looks like a generic Win32 frame around a custom application.

## A fresh download is portable by default

`tools/package_release.ps1` now writes `portable.txt` into every release zip and requires it during archive verification.
A new install therefore keeps `play`, `work`, `save`, `logs` and `reports` in `data` beside `EmblemWeave.exe` from its
first start, instead of spreading them through the Windows profile. An existing profile install is untouched: it has no
marker, so it keeps using `%APPDATA%\EmblemWeave` until **About > Storage** switches it. The switch copies saves and
leaves the old profile in place; deleting `portable.txt` goes back.

## CMake 4.5.0-rc3 is a version (#35)

The build's own version reader split on `.` and required every part to be a number, so `cmake version 4.5.0-rc3` produced no
version at all and the build said `CMake was not found on PATH`. The Requirements page used a reader that already dropped
the `-rc3` suffix, which is why it said installed in the same window.

Both now read the leading numeric part of the token, so `4.5.0-rc3`, `4.4.4,` and `v1.13.2` compare as `4.5.0`, `4.4.4` and
`1.13.2`. A test covers the exact version from the report.

## A reused old engine is refused instead of crashing (#34)

`built_by` records the launcher that wrote `fefw.ini`, not which `fefw.exe` is beside it. A rebuild that reused an old
engine could therefore claim 0.1.32 while still carrying the reader from before packed-package support, and the package
died on `main.npdm is compressed in the .nup`.

A build from this release writes `[engine] packed_nup = 1`. Play refuses a package that keeps files packed only when
neither that marker nor a written `[fs] romfs_overlay` folder is present, even when `built_by` is current, and names the
reused engine and the rebuild that fixes it. A 0.1.20 through 0.1.33 build with the overlay Play writes still plays, and
a current build of the same package still plays.

Startup also checks `built_by`. An older folder gets a warning and **Repair / Rebuild now** on Overview. That button is
different from **Rebuild**: it deletes `game-build/fefw/build` first, so an old `fefw.exe` and its objects cannot survive an
incremental build, then compiles the runtime in the folder again. If the engine sources themselves are older than the
launcher, the repair cannot replace them; unzip this release into a new folder in that case, which the button's tooltip says.

## The clang++ build folder is repaired once more (#9)

The build scripts already start over a folder configured for the wrong compiler, but a configure that swaps the compiler
after its first pass could still leave one behind. When the log carries `unknown argument: '-clang:...`,
`no such file or directory: '/W3'` or `unknown argument: '-fmacro-prefix-map`, the launcher now deletes the configuration
folders and lets the script configure from nothing, once, before reporting the failure. The repair build on Overview also
clears the whole runtime build folder, which covers a cache that survived the first retry.

## Upscaler files in an extracted SDK are found (#26 and #29)

The Graphics page looked for `upscalers\fsr`, `upscalers\streamline` and `upscalers\xess`, then one level down. An SDK
archive extracted as it came keeps its DLLs in `bin`, `bin\x64` or `x64\bin`, two or three levels down, and the original
project calls the folder `upscaler`, not `upscalers`.

Detection now accepts both folder names and walks vendor folders up to three levels. **Look for the files** also searches
inside extracted SDK trees whose folder names a vendor, instead of only the top level. The same package, including the
`.nup` reader and `.nx` archive reader, is unchanged.

## Saves load from the title's own account folder (#10)

The save loader looked through `save_dir` and picked the most recently written account folder. A second profile, or an
emulator that wrote a new folder, could therefore become the target even though the game always reads
`account/DEFAULT_USER`. The loader now uses that fixed folder, validates the profile before loading it, and says what is
missing instead of failing silently inside the engine.

The Saves page shows the current slot and profile, makes Load the primary action, marks the installed save, and keeps a
backup list. Restore writes a backup back to the slot, and Open folder goes straight to the file. Import and export keep
the emulator layout they already used.

## Shader translation no longer spins every core (#10)

The translator and the runtime shader pools defaulted to one worker per logical processor. On a 24-core laptop that meant
24 compiler threads, which is why a compile burst could reach 6 GHz and still finish late. New installs default to two
threads at idle priority with Windows efficiency mode. One setting on Graphics now writes all three runtime pools
(`nvn.gpl_threads`, `nvn.prewarm_threads`, `nvn.shader_preload_threads`), and the CPU presets are Quiet, Balanced and Fast.

## Controller vibration can be tested and switched (#10)

Controls has a **Test vibration** button that rumbles every connected XInput pad for half a second, so a missing motor or
a disconnected pad is obvious before Play. Auto remains the default, with **Standard** as a fallback for pads that only
implement the classic XInput rumble, and **DualSense** for the extended report. The choice is written to the same key the
runtime reads.

## Graphics and DLSS have their detail back (#10)

The Graphics page now exposes the runtime's own keys: renderer, resolution scale, upscaler (DLSS, FSR, XeSS and the
native path), sharpening, frame pacing, VSync, the shader pool and the CPU preset. Each control says which `fefw.ini` key
it writes, and unsupported upscalers are not offered just because their DLL happens to be on disk.

## The dashboard is modern, and still EmblemWeave

The old outlined glass and serif display type are gone. Navigation is a flat rail with one filled row for the current
page, cards are quiet 16 pixel surfaces with a single hairline, and controls are 10 pixel rounded rectangles. Headings use
the same humanist sans as the site, the XiON palette is unchanged, and the logo, pages, labels and workflows are the ones
users already know. The Overview hero, status cards and warning cards keep their positions.

## Overview is a main-menu carousel

The landing page now opens on a centre-focused carousel instead of only a hero and status cards. The front card glows,
the cards on either side preview the neighbouring sections, and clicking the front card opens Play, Setup, Saves, Mods,
Cheats, Recompilation, Graphics, Audio, Controls or About. The arrow buttons, dots and arrow keys while hovering all move
the selection. The card height follows the window, side cards drop out before they can be clipped, and the controls sit
inside the card row at every supported size. The left navigation is unchanged, so the carousel is a faster path to the
same pages, not a replacement for the rail.

## About carries every mirror and a credits marquee

The About page now links the project site, GitHub, GitLab, GitGud and the Cloudflare fallback as brand-coloured tiles,
and states that no account is needed for the mirrors. The credits are one slow horizontal strip that pauses on hover, in
the same spirit as the comment marquee on xiondigital.net. The old arcade link is gone; the site link is the EmblemWeave
page itself.

## Graphics tells players where the upscaler DLLs come from

Each missing upscaler on Graphics now has a button to its vendor's official download page. A Setup guide window names the
exact DLLs, the folder each belongs in (`upscalers\\fsr`, `upscalers\\streamline`, `upscalers\\xess`) and the runtime or
GPU requirement. The guide also opens the upscalers folder and repeats that files must not be renamed.

## The site follows the latest release

`docs/site.js` reads `docs/release.json`, then the GitHub releases API, and updates the version chip, release badge,
download link and the stylesheet query string. A new tag therefore changes the site without a hand edit, and a new palette
cannot be hidden behind a cached `site.css`. The workflow stamps `release.json` and the static fallback, commits and pushes
them, then runs `tools/smoke_site.py` against the live URL with retries while Pages deploys. It fails if the version, CSS
URL or palette is stale.

## Releases are built by CI, not by this PC

`.github/workflows/release.yml` runs on a `v*` tag. It checks that the tag matches `Cargo.toml` and has a changelog,
packages and re-extracts the Windows zip, configures the extracted engine, builds the Linux shader translator on Ubuntu,
records its executable bit, writes SHA-256 hashes and release notes, creates the GitHub release, stamps the site, and runs
the post-deploy smoke check. `workflow_dispatch` with `dry_run: true` performs the build and verification without
publishing. The local `release.ps1` still works for a Windows zip, but the published release no longer depends on it.

## The packed-package parser is tested against real bytes

`crates/ew-format/tests/fixtures/tiny.nup` is a checked-in 711 byte container made by `make_nup.py`, with a real header,
metadata table, file table and string table. `nup_fixture.rs` opens and reads it, then mutates and truncates its tables,
offsets, names and ranges in more than a hundred cases and requires an error rather than a panic. The packed-package guard
and `Nup::open` are now covered by bytes, not only by hand-built structs.

## Already fixed, for the reports that still point at older releases

- **`.nx` archives (#28):** the engine reader returned in 0.1.31 and reads the archive in place. Point Game Setup at the
  `.nx`; nothing is copied out.
- **Portable mode (#29):** every current release zip carries `portable.txt`, so an unpacked download keeps its data
  beside the program from the first run. **About > Keep everything in this folder** switches an existing profile copy,
  and `--portable` does the same without the window.

## Documentation

The README is now a landing page rather than a 700-line manual. Security, installation and game data, the page-by-page
launcher guide, and building and testing each have their own page under `docs/`, linked from a short README summary; the
long development status, roadmap, capabilities and requirements sections collapse behind `<details>`. The portable
behaviour, the release contents and the new legal pages are linked in the same place, and the release zip now carries
every guide page and screenshot the README links instead of only `PACKAGE.md`. `docs/TERMS.md` covers piracy,
free and open-source distribution, no donations or monetisation, intellectual property and the contributor policy;
`docs/PRIVACY.md` states what stays local and exactly what a report bundle contains.
