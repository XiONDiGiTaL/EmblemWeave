# EmblemWeave 0.1.33

> The launcher builds the lifted code for the processor it is running on, and Diagnostics says which build that is.

## What's new

- **The CPU is probed before the build.** SSE4.2, POPCNT, CMPXCHG16B, AVX and FMA3 are read with CPUID and XGETBV, and the launcher chooses between the engine's two builds of the lifted code: `fma` (FMA3 + AVX, the faster one) and `compat` (SSE4.2 + POPCNT + CMPXCHG16B, no FMA3).
- **The choice reaches both CMake projects.** It is passed as `FEFW_CPU_VARIANT`, which sets `-mfma` only for the `fma` build, and records the variant in the lift library. Until now the launcher's CMake path passed `-mfma` unconditionally, so the engine's compat build could not be reached from the launcher at all.
- **A processor that can run neither build is refused up front**, with the missing instruction sets named, instead of a build that compiles and then stops with exit code 4. The engine's own check and its message are unchanged.
- **Diagnostics → Runtime has a "This PC" section**: CPU brand, the instruction sets found, the build chosen, or the warning explaining why there is none.
- **The docs now describe the engine that exists.** fefw-recomp is the integrated primary engine; the Rust crates are supporting verification and experimental tools, not a replacement runtime. The pipeline diagram, component table and project structure follow the real engine, the CPU requirements are stated as SSE4.2/POPCNT/CMPXCHG16B with FMA3 as an optional faster build, and `docs/GRAPHICS.md` records what the engine implements (TAAU, FSR 1, NIS, FSR 3.1, DLSS/DLAA, XeSS), what was evaluated and not integrated (FSR 4, frame generation, OptiScaler, ReShade, vkBasalt), and why.
- **A site, at [xiondigital.net/EmblemWeave](https://xiondigital.net/EmblemWeave/)**, with a static fallback page served from Cloudflare outside GitHub, and a GitLab source mirror.

## Fixes for reported issues

- **#30, "CMake was not found on PATH" while CMake is installed.** The requirements page probes tools through the environment `vcvars64.bat` sets, which includes the CMake that ships inside Visual Studio; the build probe used only the launcher's own PATH, so that copy was invisible. The build probe now searches Visual Studio's bundled CMake, the 32-bit CMake folder, Chocolatey and Scoop as well.
- **#34, the game stopping on `main.npdm is compressed in the .nup`.** The current engine decompresses zstd entries on their first read, so this is an engine older than 0.1.20 being used from a mixed game folder, usually a new `EmblemWeave.exe` dropped into an old extracted release. Play now refuses that combination and says which version built the folder, instead of letting the old engine die two seconds in.
- The site is restyled to the palette and type of xiondigital.net and lists only mirrors that exist.
- **Code mods (#36):** Overview warns next to Play when installed code mods bring hook sites the built game lacks, and both it and Mods name a broken `.sites` file before a build is pressed. The engine also stops keeping a merged `FEFW_SITES` in its cache, including folders configured by an older launcher, so a build without code mods goes back to `main.sites`.
- **Program icon:** the new winged EW artwork is the launcher's and the built game's icon, at every size Windows asks for.

## Verification

- `cargo test -p emblemweave`: 129 passed, 10 ignored.
- The FMA build links and starts; `FEFW_CPU_FORCE_MISSING=fma,avx` exits with code 4 and a message naming FMA3 and AVX.
- A synthetic game folder built by 0.1.10 and pointed at a zstd-packed `.nup` is refused by Play with the rebuild message; the same folder marked as built by this release is not.
- The compat build configures with `lifted code: compat build (SSE4.2 + POPCNT, no FMA3)`, has no `-mfma` in the generated build files, and its stub compiles with `FEFW_CPU_NEEDS_COMPAT_BUILD`. The full compat game has not been played here: that needs a processor without AVX, or a deliberate compat build on this one.
