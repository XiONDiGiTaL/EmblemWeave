# EmblemWeave v0.1.42 - Release Validation Checklist

- **Purpose:** one repeatable pass from a clean canonical `main` to a publishable artifact.
- **Rule:** compilation is not gameplay validation. A build item can pass on a compiler result; startup, transitions,
  cinematics, HDR and long-session items require a running game and recorded evidence.
- **Evidence:** keep every log, hash, screenshot and report under `target/validation/<YYYYMMDD-HHMMSS>/`. Do not paste
  user paths, saves or secrets into release notes.
- **Authorization:** stop before tagging, publishing or deploying unless the owner explicitly authorizes it.

Record at the top of the run:

```
commit:
branch: main
worktree clean:
operator:
date:
machine:
GPU / driver:
game build ID:
toolchain (rustc, cargo, MSVC, CMake, Ninja, Python):
```

## 0. Preconditions

- [ ] FCC handoff is complete and its intended changes are committed.
- [ ] `git status --porcelain` is empty except for explicitly preserved files.
- [ ] The preserved stash has been reviewed; nothing is applied over FCC's work.
- [ ] A current E: user-data backup exists and its checksums verify.
- [ ] Release metadata is cut only after the engine pass; until then `check_release.py` must still name 0.1.41 as
      published.
- [ ] The Vulkan validation layer is installed for the test run.
- [ ] A supported game build (1.1.0 / 131072) and a scratch install location are available.

## 1. Clean launcher build

```bash
mkdir -p target/validation/src
git archive --format=tar HEAD | tar -x -C target/validation/src
cargo build --release -p emblemweave --locked --manifest-path target/validation/src/Cargo.toml
```

- [ ] Exit 0; full log retained.
- [ ] Record size, SHA-256 and Windows file version (must be 0.1.42).
- [ ] Record `Cargo.lock` SHA-256 and `rustc`/`cargo` versions.
- [ ] Confirm no file outside `target/validation/src` contributes to the binary.

Pass: reproducible artifact from the recorded commit. A dirty-tree build is not a pass.

## 2. Clean production engine build

Build from the same clean archive or a clean checkout of the recorded commit, with no FCC working-tree files.

```powershell
# From the launcher: Build the game, or the engine's documented build script.
# Retain the complete build log and the compiler/dependency versions.
```

- [ ] Exit 0, all stages complete, no missing dependency.
- [ ] Record `fefw.exe` size, SHA-256, build time and compiler versions.
- [ ] Confirm the binary's source commit is the recorded canonical commit.
- [ ] Confirm no binary from `E:\EmblemWeave`, FCC's tree or a previous session was reused.
- [ ] Record the shader translator, CMake, Ninja, MSVC and Python versions.

Pass: a fresh `fefw.exe` that can be traced to the recorded commit. Copying an existing binary is not a pass.

## 3. Launcher tests

```bash
cargo test -p emblemweave --locked
```

- [ ] Record the exact summary line and exit status.
- [ ] Expected baseline: 427 passed, 0 failed, 13 ignored.
- [ ] List every ignored test and confirm each ignore is pre-existing and justified.
- [ ] Do not add `#[ignore]`, weaken assertions or filter failures to improve the count.

Pass: 0 failed, no new ignores. A different pass count is acceptable only with an explained diff.

## 4. Engine tests

Run the built engine's test binary in a normal desktop session with the Vulkan validation layer installed.

- [ ] Record the full summary line, exit status and total test count.
- [ ] Confirm the run completed; a stall without a summary line is **incomplete**, not a pass.
- [ ] Triage every failure:
  - environmental (layer/controller) with the evidence that proves it;
  - hardware-specific with the queried capability, not a hardcoded expectation;
  - code-level with a baseline/bisect, not the label "pre-existing".
- [ ] Fix the AMD subgroup test to query `VkPhysicalDeviceSubgroupProperties`.
- [ ] Install the validation layer in CI; do not delete tests that require it.
- [ ] Keep `kernel_sync` (heap corruption), `soak`, `svc_fs_romfs`, `svc_info`, `svc_memory`, `tt_live` and
      `write_watch` open until each is explained.

Pass: completed run, every failure classified with evidence, no suppression.

## 5. Runtime dependency verification

- [ ] `avcodec-62.dll` SHA-256 `c202c131bb051e2298aaf5aca2571fc65d2e781ac07568c63c925b6d4e128877`
- [ ] `avutil-60.dll` SHA-256 `1645ea1d5774d07304731f842e6b16507f5000c331cca3cf6d71346ebc02541b`
- [ ] `swresample-6.dll` SHA-256 `ce4dce3d71ea83c49cc332437fd61fe847fa055f4f25a9cf120fd4f41294f1c4`
- [ ] Licence texts and source notes are present beside the DLLs.
- [ ] `dumpbin /dependents fefw.exe` (or an equivalent inspection) shows no missing runtime DLL.
- [ ] The launcher writes the correct `[media] ffmpeg_dir` for a portable install.
- [ ] A start with the DLLs removed reports the missing file by name and does not crash.

Pass: hashes match the manifest and the engine starts with the bundled set.

## 6. Portable installation

- [ ] Unzip the package into a new scratch folder; do not test inside `E:\EmblemWeave`.
- [ ] `portable.txt` is present and empty.
- [ ] Settings, saves, logs and build output stay under `data\` beside the exe.
- [ ] No `%APPDATA%\EmblemWeave` write is needed for a fresh portable install.
- [ ] Build and Play work from a path with spaces; record the path.
- [ ] Removing the scratch folder leaves no required state outside it.

Pass: a self-contained install. A portable folder that silently reads `%APPDATA%` is not a pass.

## 7. Existing installation upgrade

- [ ] Copy an existing install (including `data\`) to a scratch folder. Never upgrade `E:\EmblemWeave` for this test.
- [ ] Record a SHA-256 manifest of `data\save`, `data\config.json`, `data\play\fefw.ini` and `mods\` before the overlay.
- [ ] Overlay the candidate package the way the updater does.
- [ ] Re-hash the same paths; only intended files may change.
- [ ] Confirm the built game is preserved or rebuilt only for a stated reason.
- [ ] Confirm the launcher starts, detects the game and shows the correct version.

Pass: upgrade preserves user data and the built game. A clean install is not an upgrade test.

## 8. Save and profile preservation

- [ ] Count every save file and record a SHA-256 manifest before and after startup, Play and exit.
- [ ] Existing profiles still list and load.
- [ ] A new profile does not overwrite the current save; a backup is made.
- [ ] Restoring a backup returns the exact previous slot set.
- [ ] Autosave slots are discovered.
- [ ] Migration from 0.1.41 is tested on a copy, including a stale absolute `save_dir`.
- [ ] Launcher and runtime agree on the effective folder (`Config::save_dir()` and `[fs] save_dir`).
- [ ] No test is run against the only copy of a user's saves.

Pass: the game loads the expected save after restart and after the update. A launcher badge is not evidence.

## 9. Mod preservation

- [ ] Record hashes of `mods\` and the active mod list before the upgrade.
- [ ] RomFS mods still overlay package data.
- [ ] Code mods (`exefs\*.dll`) still load, or the refusal names the reason.
- [ ] A rebuild triggered by an active-set change does not delete the mods.
- [ ] Conflict/refusal messages are specific and do not silently ignore a mod.

Pass: the same mod set is active and behaves the same after the upgrade.

## 10. Game-data validation

- [ ] Use a supported 1.1.0 / 131072 dump or `.nup`.
- [ ] Record the RomFS file count; the expected complete package is 252,686 files.
- [ ] The launcher's verdict names the build ID and does not accept an unsupported build silently.
- [ ] The dump is not modified; verify its hash before and after.
- [ ] A 1.1.1 tree is either accepted with evidence or refused before a long build, naming the supported IDs.
- [ ] DLC discovery is recorded separately; missing DLC is not reported as corrupt base data.

Pass: a supported dump builds and the validator's verdict matches the data.

## 11. Diagnostic report and ZIP generation

- [ ] Generate the report bundle from Diagnostics/Troubleshooter.
- [ ] Inspect the ZIP: settings, newest task logs, game log, freeze/crash report and save reconciliation status.
- [ ] Confirm no save contents, game files, credentials or unrelated personal paths are included.
- [ ] Confirm the ZIP opens on a clean machine and the text is readable.
- [ ] Confirm the engine's freeze report records private commit, working set, guard footprint/limit, system RAM/commit
      and presented frames.
- [ ] Attach nothing automatically; the user decides.

Pass: a complete, redacted, readable bundle. A bundle that omits the freeze report is not a pass for a freeze.

## 12. Gameplay startup

- [ ] Launch from the launcher, not only directly from `fefw.exe`.
- [ ] Reach the title screen with the game's own rendering (not a black window).
- [ ] Continue into the first map/hub.
- [ ] Confirm audio, input and save recognition.
- [ ] Record the startup log, the title screenshot and the time to first full frame.

Pass: the game is playable. A process that stays alive or a headless run is not gameplay startup.

## 13. Scene transitions

- [ ] Perform at least 10 menu <-> title transitions in one session.
- [ ] Enter and leave gameplay, open the in-game menu, return to title, repeat.
- [ ] No `HOST EXCEPTION`, retired-page fault, hang or device loss.
- [ ] Memory and frame times remain stable across cycles.
- [ ] Retain the log and the cycle count.

Pass: 10+ cycles without a crash. One 120-second session does not satisfy #77.

## 14. Cinematic playback

- [ ] Trigger at least one AV1 + Opus cinematic from the real game data.
- [ ] Video displays without corruption.
- [ ] Audio decodes and stays in sync for the whole clip.
- [ ] No crash at entry, during, or at exit.
- [ ] Record whether hardware acceleration is active and the observed frame rate at the target resolution.
- [ ] Repeat with the software decoder path if the hardware path is claimed.

Pass: end-to-end playback with sound. A build that contains dav1d is not playback evidence.

## 15. HDR restoration

Run the full matrix in `docs/audits/V0.1.42_RELEASE_READINESS.md` section 6.1:

- [ ] HDR initially off, SDR game, normal exit.
- [ ] HDR initially on, HDR10 game, normal exit.
- [ ] HDR initially off, forced HDR, normal exit.
- [ ] scRGB where supported.
- [ ] Fullscreen and borderless.
- [ ] Normal exit / window close.
- [ ] Return-to-title.
- [ ] Initialization failure.
- [ ] Swapchain recreation.
- [ ] Monitor move, unplug/replug, primary change.

Record the Windows advanced-colour state, SDR white level, resolution and refresh before and after each case. Forcing
windowed mode is not a pass.

## 16. Extended gameplay stability

- [ ] Run a 2+ hour session for #37 with memory, commit, working set, audio voices and frame times recorded every
      minute.
- [ ] Run the #41 failing scene (past Chapter 12) on a 16 GB shared-memory device and on a 24 GB comparison device.
- [ ] Test Low Memory profile on and off; record `heap_gb`, `limit_gb`, commit, working set and video budget.
- [ ] Record any device loss with `fefw_freeze.txt`, `nxrt.log` and the driver version.
- [ ] Do not report a fix for #41 unless the failing scene completes on the affected hardware.

Pass: the sessions complete, or the report proves which limit was reached. A short run is not an extended-session pass.

## 17. Linux compatibility status

- [ ] Record FCC's Linux/Vulkan status and the commit it applies to.
- [ ] Verify the release zip uses forward-slash paths and extracts on Linux.
- [ ] Test the documented Proton/Steam Deck route on real hardware if it is claimed.
- [ ] Do not convert "a Windows build runs under Proton" into "native Linux support".
- [ ] If Linux is unverified, say so in the release notes.

Pass: the documented route is exercised, or the limitation is stated.

## 18. Packaging and final sign-off

- [ ] Cut `docs/release.json`, the download button, the README status line and the changelog index only after the

- [ ] `python tools/check_release.py` passes for 0.1.42.

- [ ] Re-run the package verifier and inspect the zip contents.
- [ ] Deploy to E: only after the deployment plan's pre-checks pass and a fresh backup exists.
- [ ] Tag, publish and deploy only with explicit authorization.
