# EmblemWeave v0.1.42 - Release Readiness Audit

- **Audit date:** 2026-11-24
- **Auditor:** Freebuff (independent of FCC)
- **Audited source:** `113cc8faff98138544fbc4c6825b3590809ca491` on `main`
- **Verdict:** **NOT READY TO PUBLISH.** The Freebuff launcher work is consolidated and builds cleanly, but the
  production engine has not been built from canonical source, the headline runtime fixes are not field-verified,
  one reported crash class (#41) has no implementation, and the existing release documents contradict the tree
  and each other.

This audit checked implementation and executable evidence rather than accepting the release documents. Claims
that could not be reproduced are marked as such.

## 4. Engine tests - not independently rerun; documentation unreliable

The existing documents report 14 failing tests and 69 assertions, but the counts disagree with each other:

- `TEST_KNOWN_ISSUES.md`: 166 pass, 14 fail, 5 skip, 185 total; "91% (166/182)".
- `REMEDIATION_SUMMARY_v0.1.42.md`: "931 passed, 14 failures, 29 skipped".
- `INDEPENDENT_ISSUE_VERIFICATION.md`: "All engine tests pass (1000+)".

These cannot all describe the same build. The summary's category table also says "5 Pre-existing Code Issues"
but lists **nine** test names (`kernel_sync`, `kernel_threads`, `soak`, `svc_fs_romfs`, `svc_info`, `svc_memory`,
`tt_live`, `write_watch`, `launcher_game_info`). The 69-assertion total (44 + 19 + 1 + 5) is therefore arithmetic
built on a mislabeled category, not a verified assertion count.

Classification audit:

| Category | Claimed | Independent assessment |
| --- | --- | --- |
| Missing Vulkan validation layer (44) | Environmental | **Partly accepted.** The assertions explicitly require the layer. That is an environment gap, but it also means those 44 checks provide zero Vulkan validation coverage in this environment. The layer must be installed in CI rather than the tests deleted. Missing layers do not excuse defects the tests were meant to catch. |
| Physical gamepad (19) | Environmental | **Accepted.** No controller was attached. A mock HID device should be used in CI. |
| AMD subgroup 64 vs 32 (1) | Hardware difference | **Accepted, and the test is wrong.** AMD's 64 is valid under Vulkan; the test should query `VkPhysicalDeviceSubgroupProperties` instead of hardcoding 32. |
| Nine code-level tests | "Pre-existing" | **Not accepted as proven.** `kernel_sync` reports heap corruption (0xC0000374), `soak` and others SEGFAULT. No bisect or baseline from a known-good commit is attached. Labeling them pre-existing without evidence is exactly the pattern this audit was asked to stop. They are at minimum **High** until triaged. |

The engine tests were not rerun here because there is no canonical engine build and FCC's files are active.
This is a limitation of this audit, not a pass.

### #79 evidence review

Both reporter bundles were opened and compared:

**kalhawke** - v0.1.41 (`a56d1e2`), portable install at `G:\Games\EmblemWeave-v0.1.40`, extracted RomFS game
root, `save_dir = G:/Games/EmblemWeave-v0.1.40/data/save`. The report shows a profile being moved into
`data/save/backups/...-profile-First Run 0.1.41` before launch. The launcher log shows a successful start and
first frame, but no evidence that the player's saves were rediscovered afterwards.

**msalgadob** - v0.1.41 (`a56d1e2`), portable install at `D:\switch\EmblemWeave-v0.1.41`, 252,693-file `.nup`
read in place with 65,080 zstd-compressed files, `save_dir = D:/switch/EmblemWeave-v0.1.41/data/save`. The
player states that after four hours the next-day session started from zero, and that checking backups and
creating a profile did not help.

Both are on 0.1.41, before the 0.1.42 reconciliation code. The current tree does contain:

- `sync_save_dir()` before Play, which must stop rewriting the INI to the launcher folder (#79 R1).
- Mismatch warnings and effective-folder display in Game Setup / Saves (R2).
- `find_orphan_saves()` / `adopt_orphan_save()` with consent and backup (R3).
- Loud save-directory creation logging and diagnostic bundle reconciliation status (R4/R5).

None of this has been exercised by either reporter or by this audit. The **specific failure mode** in the
reports - saves present on disk but the game starting from zero - is not demonstrated fixed. The profile backup
restoration path is a recovery aid, not proof of discovery. Until a reporter (or a faithful reproduction with
the same portable `.nup` layout) confirms saves survive restart and update, #79 must stay open and the
changelog's "save directory reconciliation implemented" wording must not be read as "save loss fixed".

## 8. Severity summary

**Critical (prevents publication)**

1. No canonical production engine build; FCC's 24 modified engine files are unintegrated.
2. #79 save loss has two reporters and no field confirmation of the 0.1.42 reconciliation.
3. Release documentation cannot be trusted: stale hashes, contradictory test totals, wrong runtime path.

**High**

4. #41 has no fix and is not listed as a known issue in the draft notes.
5. #77's required repeated title-return test was not performed.
6. #78 does not restore the original HDR state; it forces windowed mode.
7. Nine engine test failures, including heap corruption and SEGFAULTs, are unclassified and were called
   "pre-existing" without evidence.
8. #37 long-session stability and audio lifetime remain unproven; profiling is uncommitted FCC work.

**Medium**

9. #70/#75 cinematics are build-verified only.
10. #76 Find Units has no in-battle measurement.
11. #59's fix exists but its performance claim was not independently reproduced.
12. #7 Linux compatibility and #26/#29 upscaler compatibility lack hardware evidence.

**Low**

13. Test-only hardcoded `E:/FEFW` paths.
14. Ignored tests and missing Vulkan layer reduce coverage but are documented.

## 9. What must happen before v0.1.42 can be published

1. FCC commits its MAKO/Vulkan work; Freebuff reviews and integrates it into `main`.
2. Build the production runtime from the final canonical commit; record compiler, dependency and binary hashes.
3. Rerun the engine test suite and triage the nine code-level failures, including the heap-corruption and
   SEGFAULT cases; install the Vulkan validation layer in CI.
4. Field-test #79 with a portable `.nup` install: create a save, restart, update, and confirm discovery. Test the
   orphan-adoption and backup-restoration paths.
5. Run the #77 repeated title-return test and an extended #37 session; verify HDR state restoration on #78.
6. Add #41 to the known-issues section or fix it before release.
7. Correct the release documents' hashes, test totals, runtime paths and commit references.
8. Cut the release metadata (release.json, download button, README, changelog row), then build and verify the
   v0.1.42 zip, sidecars and checksums.
9. Deploy to E: only after the pre-deployment validation in `V0.1.42_DEPLOYMENT_PLAN.md` passes.
10. Publish only with explicit authorization.
