# EmblemWeave v0.1.42 - Release Readiness Audit

- **Audit date:** 2026-11-24 (follow-up pass)
- **Auditor:** Freebuff (independent of FCC)
- **Audit base:** `6646b5f7641ddc3b74cef49ef11a826f7b0a9504` on `main`
  (a documentation-only commit over the audited code at `113cc8faff98138544fbc4c6825b3590809ca491`).
  These corrections were committed to `main` after that base; the audited code remains `113cc8fa`.
- **Verdict:** **NOT READY TO PUBLISH.** The launcher is consolidated and reproducible, and this pass corrected the
  release documents. The production engine still has not been built from canonical `main`, FCC's active engine refactor
  (25 modified/deleted and 13 untracked paths at the final check) remains unintegrated, #79 has no field confirmation,
  #78 does not restore the original display state,

  triaged.

This audit records implementation and executable evidence. Claims that could not be reproduced are labelled as claims.
It deliberately does **not** name a definitive production-runtime hash: no production runtime has been built from
canonical `main`.

## 6. Issue assessments

### 6.1 Issue #78 - HDR state after exit

**Status: Partially implemented. The original display state is not captured or restored.**

What exists:

- `engine/fefw-recomp/runtime/src/gfx/play/play.cpp` `stop()` (lines 1549-1552) calls
  `platform::set_fullscreen(FullscreenMode::Windowed)` when the window is not already windowed.
- `engine/fefw-recomp/runtime/src/gfx/extras/win_display.cpp` queries Windows advanced-colour state and luminance.
  It is **read-only**.
- `vk_renderer.cpp` chooses an HDR10/scRGB swapchain and sends `VkHdrMetadataEXT`. That describes the swapchain; it
  does not save or restore a display configuration.
- `device_lost()` in `vk_renderer.cpp` is a terminal path. It writes a report and exits; it does not restore anything.

Why forcing windowed mode is not restoration:

- If Windows HDR was off before launch and the game switched it on (or left an HDR mode behind), forcing the window
  to windowed does not necessarily turn Windows HDR off.
- If Windows HDR was on before launch, forcing windowed does not preserve the SDR white level, resolution, refresh
  rate or HDR10/scRGB choice the player had.
- If exclusive fullscreen changed the display mode, `SDL_SetWindowFullscreen(false)` returns the window to desktop
  size but is not a verified restore of the display's previous mode.
- Borderless mode is not handled by the stop path at all.
- Initialization failure, device loss and crash paths never reach `stop()`.

Required implementation (to be owned or explicitly handed off by FCC, because it touches files FCC is editing):

1. Before any fullscreen/HDR change, snapshot each affected monitor:
   - Windows advanced-colour enabled state (`DISPLAYCONFIG_GET_ADVANCED_COLOR_INFO`),
   - SDR white level (`DISPLAYCONFIG_SDR_WHITE_LEVEL`),
   - current resolution, refresh rate and orientation,
   - the swapchain output kind (SDR8, HDR10, scRGB) and the HDR metadata actually sent.
2. Record whether **this process** changed each value. Never overwrite a user's manual change made during play.
3. Restore only the values this process changed, using the supported display-configuration APIs where Windows permits
   it. If a restore is refused, log the exact refusal and leave a manual-recovery instruction; do not claim success.
4. Run the restore from every exit path: normal quit, window close, return-to-title if play mode changes output,
   swapchain recreation, initialization failure, device loss and the fatal/crash path where possible.
5. Re-query after a monitor move, unplug/replug or primary-display change; keep one snapshot per display.
6. Log a before/after line per display so a field report can prove the result without a screenshot.

Required test cases (all currently **unverified**):

| # | Initial state | Action | Required result |
| --- | --- | --- | --- |
| 1 | Windows HDR off | Start SDR, quit normally | HDR still off; resolution/refresh unchanged |
| 2 | Windows HDR on | Start HDR10, quit normally | HDR still on; SDR white and mode restored exactly |
| 3 | Windows HDR off | Force `[hdr] mode = on` (HDR10), quit | HDR off again; no HDR mode left behind |
| 4 | Windows HDR on, scRGB supported | Start scRGB, quit | scRGB swapchain gone; desktop state restored |
| 5 | HDR10 display | Fullscreen exclusive entry and exit | Previous display mode, refresh and HDR state restored |
| 6 | HDR10 display | Borderless entry and exit | Same restoration; borderless is not skipped |
| 7 | HDR on or off | Return to title from gameplay | Title keeps the intended state; no repeated or drifting restore |
| 8 | Any | Initialization fails before the first frame | No stuck fullscreen/HDR state; failure is reported |
| 9 | Any | Swapchain recreation (resize/mode change) | One snapshot, one restore; no duplicate or partial restore |
| 10 | Two monitors | Move window, unplug/replug, change primary | Each changed display restored; untouched display unchanged |
| 11 | Any | Device lost or fatal crash | Best-effort restore; report says whether it succeeded |

Do not edit `play.cpp`, `platform_win32.cpp`, `vk_renderer.cpp` or the display helpers while FCC owns them. This
follow-up changed no runtime code.

### 6.3 Issue #41 - crashes past Chapter 12 on shared-memory hardware

**Status: Outstanding. No fix, and no reproduction in this audit.**

Evidence available:

- The remediation matrix records #41 as **NOT STARTED**, with one `fefw.log` attachment and no analysis.
- `docs/ROADMAP.md` records the #41 report as a **1.1.1** run on a 16 GB shared-memory profile that lost the device
  after about 400 seconds. The 1.1.1 build is not a verified supported build.
- The full #41 log and report bundle are not in the repository, so this audit cannot confirm a cause.
- The failure is a device loss, not the #37 audio/RAM leak. The two must not be merged.

Existing memory-management controls:

| Control | Value / behaviour |
| --- | --- |
| `[memory] heap_gb` | heap section reserve; 12 GiB default on the Switch 2 path (6 GiB otherwise), 1-1024 accepted |
| Guest memory ceiling | `svc_total_memory()` reports 10.5 GiB on the Switch 2 path; `SetHeapSize` refuses more than the ceiling |
| `[memory] limit_gb` | host-memory guard; 16 GiB default on the Switch 2 path (8 GiB otherwise) |
| Memguard | polls private commit every 250 ms, warns at 75%, writes `fefw_freeze.txt` and stops at 100% |
| Video-memory discount | only a discrete GPU's dedicated heap is subtracted; an integrated GPU subtracts nothing |
| Low Memory profile | 1280x720, render scale <= 0.75, scene scale <= 75, FSR 1 if upscaling is off, performance quality, frame generation off, ASTC Fast, one compile thread at idle |
| Texture residency | demotes unused textures near the video-memory budget; `[gfx] residency` |
| Video decode | bounded packet and picture queues |
| Opus decoder | freed with the service (#37 partial) |
| Device loss | **terminal**: report and exit; no recovery |

Actual limitation on shared-memory hardware:

- On a 16 GB device the GPU and the game share physical memory. A 12 GiB heap-section reserve plus the runtime, the
  driver and the compositor leaves little headroom even before a scene opens many voice banks.
- The guard measures **private commit**, not resident physical memory or the driver's shared allocation. Windows can
  page and the driver can lose the device while private commit remains under 16 GiB. The guard therefore cannot be
  presented as a fix for this class.
- The Low Memory profile lowers render and texture cost but does not change `heap_gb`, `limit_gb`, or the guest heap
  ceiling. It is a mitigation, not a proven fix.
- AMD integrated GPUs do not receive the Intel-only `budget_detail`/`pressure_detail` defaults; the external
  compatibility audit records that gap.
- When the device is lost, the runtime writes a report and exits. A player cannot recover the session.

Classification: **outstanding issue; release blocker for any claim that 16 GB shared-memory handhelds are supported,
and a mandatory known limitation if v0.1.42 ships for that hardware.** It is not proven to be a 0.1.42 regression, and
this audit does not invent a remediation.

Evidence required before it can be closed:

1. The full #41 `fefw.log`, `fefw_freeze.txt`, GPU driver version, game build ID, settings and memory figures.
2. A reproduction on a supported build (1.1.0/131072) on the same hardware class, and a comparison on 24 GB.
3. Before/after figures for `heap_gb`, `limit_gb`, Low Memory on/off, and commit/working set over the failing scene.
4. A decision on device-loss recovery: currently terminal by design.
