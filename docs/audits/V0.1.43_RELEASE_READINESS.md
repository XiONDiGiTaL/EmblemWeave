## 1. Issue #115 - Windows SDK 10.0.19041 build failure

### Root cause

`engine/fefw-recomp/runtime/src/gfx/extras/win_display_state.cpp` used
`DISPLAYCONFIG_GET_ADVANCED_COLOR_INFO_2` and `DISPLAYCONFIG_SET_HDR_STATE`. `wingdi.h` declares them only from
the Windows 11 24H2 SDK (10.0.26100). A build with 10.0.19041 failed at the declaration, before any HDR code ran.

### Change

Commits `a9a74e55` and `6bbc7f0b`. The file now declares both requests itself:

- `DisplayRequestHeader` matches `DISPLAYCONFIG_DEVICE_INFO_HEADER` (size, field offsets asserted).
- `AdvancedColorInfo2` matches `DISPLAYCONFIG_GET_ADVANCED_COLOR_INFO_2`: size 36, flags at 20, encoding at 24,
  bits per channel at 28, active colour mode at 32.
- `SetHdrState` matches `DISPLAYCONFIG_SET_HDR_STATE`: size 24, value at 20.
- Request numbers 15 and 16 are `UINT32` constants. They are not cast into the older SDK's
  `DISPLAYCONFIG_DEVICE_INFO_TYPE`, which clang limits to [-16, 15].
- The declarations use local names, so an SDK that defines the real types does not collide with them.

`tmp/issue115/abi_check.cpp` additionally asserts the local layouts against the SDK's own types when compiled with
10.0.26100 or 10.0.28000.

### Reproduction and ABI evidence

- Compiled against 10.0.19041.0, the pre-fix file (`94c76883`) fails with the reporter's errors:
  `unknown type name 'DISPLAYCONFIG_GET_ADVANCED_COLOR_INFO_2'`,
  `use of undeclared identifier 'DISPLAYCONFIG_DEVICE_INFO_GET_ADVANCED_COLOR_INFO_2'`, and the missing
  `DISPLAYCONFIG_SET_HDR_STATE`. This is the reported failure, not an inference.
- The current file compiles against 10.0.19041.0, 10.0.26100.0 and 10.0.28000.0.
- The ABI check compiles against 10.0.26100.0 and 10.0.28000.0 with every `static_assert` passing.
- A header-resolution probe under the pinned environment resolves `wingdi.h` from
  `D:\Windows Kits\10\Include\10.0.19041.0\um` for the 19041 build, and from `10.0.28000.0` for the newer build.

### HDR / WCG behaviour

- `read_hdr()` keeps two paths: `GET_ADVANCED_COLOR_INFO_2` first, then the legacy
  `GET_ADVANCED_COLOR_INFO` if the newer request is rejected. The newer query separates HDR from wide-colour SDR;
  the legacy query reports both as "advanced colour", so a pre-24H2 host can report WCG SDR as HDR-enabled. That
  value is only used to decide whether a restore should try a setter.
- `apply_hdr()` has no legacy equivalent: Windows exposes no public pre-24H2 setter for HDR enablement. On a host
  where `SET_HDR_STATE` is unsupported the call fails and the restore logs the request result; it does not fall
  back to a mode change or guess.
- SDR white level is captured but never written: `DISPLAYCONFIG_SDR_WHITE_LEVEL` is read-only.
- Live HDR toggling was not exercised in this pass because it changes the display. The fake-backend display-state
  tests cover the capture/restore logic; the previously recorded live test on Windows 11 26100 covers the real
  path on one display.

## 2. Issue #117 - Obelisk Chamber freeze

### Root cause

`bd90a2a3` split the kernel wait queues onto separate locks. `block_on_wake` runs the occupancy hooks while its
caller holds the mutex, CV or address lock, and those hooks take the sync lock. The split therefore created a
mutex-to-sync inversion against code that takes sync and then enters the kernel. It also reopened the gap between
handing a mutex over and queueing its waiter, where an unlock can lose the wake-up.

The failure reproduced as 236 presented frames, then a 30-second watchdog report. Main was blocked in
`arbitrate_lock` -> `block_on_wake`; guest threads were blocked in `wait_process_wide_key` -> `block_on_wake`.

### Change

- `74e7defc` reverts `bd90a2a3`. The net diff against the pre-shard tree is empty.
- `cf09114c` restores the single `detail::KernelLock g_k` for every wait queue and for occupancy, and documents why
  it must stay one lock.
- `00a114c0` keeps a timed `WaitProcessWideKey` inside its deadline.
- `b3fe4b0c` deflakes the address-waiter tests under load.

No sharding symbols remain; `grep` for the shard locks finds only the explanatory comments.

### Live retest and measurements

Recorded during this work on the installed single-lock runtime with an isolated copy of the Obelisk Chamber save:

- The chamber loaded, the Wolf Obelisk panel opened and backed out, Replay from Any Chapter opened, and the Main
  Character switch was attempted.
- No 30-second freeze and no watchdog report.
- Largest hitch across the retests: 646.9 ms during initial shader/asset warm-up.
- Post-startup frames: 151.5 ms or less (latest run: 545.0 ms startup, 151.5 ms later).
- Production save hash stayed
  `1e6a0ae1d7d164192b6ced9f74c8056793a5d01c16a8407883d8ba3593466399`; the isolated test save was restored to
  `3c1415ebb2a09ff28988c90cdbe9eca5234f77178970bc72c955208eaf70c2d8`.

**Not confirmed:** the Main Character switch itself was not visually confirmed. Shoulder, D-pad and mouse attempts
all activated the panel's focused Replay action. The kernel suite covers the sync paths the switch uses, but the
in-game switch remains a field-validation item. No new live run was made in this pass.

### Save safety

The retest used a disposable copy. The production save was not used as a fixture and its hash was unchanged. No
save-format or serialization code changed in this work.

## 7. Readiness classification

### Ready

- Issue #115: root cause reproduced, ABI asserted, full builds on 19041 and 28000.
- Issue #117: the sharding regression is reverted exactly; a single lock is in place and documented; the live
  retest reached the chamber and backed out without a stall.
- Packaging: a real package and a repeat package produce the same artifact set; `SHA256SUMS` is replaced after the
  zip and both manifests, and the stale-entry regression suite passes.
- Issue #79: the root save is discovered, the actual **Use this save** button imports eight files byte-identically,
  backs up the previous save, and leaves the source, profiles and existing backups intact on a disposable copy.
- Runtime and launcher suites pass on the candidate tree; the full ASTC-enabled engine builds and starts with the
  carried toolchain; the imported save opens and the opening AV1 movie and following scene render.
- AV1: the assembled dav1d path and the FFmpeg/D3D11VA path each decode the same 2560×1440 sample with zero late
  pictures and zero audio underruns.

### Ready with limitations

- #76: cancellation and deadline checks work between reads and all simulated blocked-read, device-loss and cleanup
  tests pass; a read already inside `ReadProcessMemory` is not interruptible, so the 30-second deadline is not a
  completion guarantee. Real in-game Find Units stall and frame-time tests are still outstanding.
- #70/#75: AV1 decode, timestamps and repeated movie playback are verified; Opus decode, seek, pause/resume and a
  measured A/V drift are not. The game's movies carry video only; audio is a separate AudRen/Opus path.
- #117 character switch: not visually confirmed in game; covered by the kernel suite only.
- #115 HDR: the setter needs Windows 11 24H2; no live HDR toggle was performed in this pass; WCG SDR can read as
  HDR-enabled on pre-24H2 hosts, and the failed setter then changes nothing.
- Bitdefender #116: the reported detection was not reproduced; no protected endpoint was available. The launcher and
  carried tools are unsigned. See `BITDEFENDER_FALSE_POSITIVE.md`.
- The runtime session was 205 s plus 98 s, not a multi-hour soak, and no title transition or damaged-save recovery
  was exercised.

### Not ready / not claimed

- #37 multi-hour memory/stability, #41 device loss on 16 GB shared-memory hardware, #70/#75 Opus/seek/pause/drift,
  #76 in-game Find Units frame time, #77 the reporter's damaged save, #78 HDR live restore, and #79 against the
  reporter's own files. The disposable click is not a claim about their installation.
- The deferred engine and launcher items listed in section 3.

**Recommendation:** 0.1.43 is suitable for **wider testing**, not a public release. The public-release blockers are
the non-interruptible #76 read path and its missing real-game measurement, unverified Opus/seek/A-V behavior, the
absence of a multi-hour soak and title-transition run, and the unresolved Bitdefender report. The #117 switch and the
#115 live HDR path should be confirmed by field reports before either is described as fully verified.
